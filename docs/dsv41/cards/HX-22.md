# HX-22: Helper-window levers: one graph launch a window, int8 rounding in the head, the T>1 publish in the routing launch
Status: kept (part of build 12) · Date: 2026-11-11
Code: in the fork's release commit. Flags: `DS4_HW_FOLD=1`, `DS4_HW_HEADQ8=1`, `DS4_HW_PUBT=1` (all default off; PUBT needs `DS4_LP_PUBFUSE=1`).

## What and why
- A re-cut of HX-20's timeline split the MI50 helper windows into two populations (MEASURED, same timestamps):
  - about 80 % of windows have no pick on that MI50 and take ~27 µs: the floor of 7 dispatches (about 3.9 µs a dispatch untraced [I]);
  - one-expert windows take ~75 µs and two-expert windows ~106 µs. These are the ones the lead waits for; about a third of each is dispatch, two thirds expert maths.
- The lead's join waits for the latest needed MI50, and a one-expert window is about 20 µs too late for the lead's own work (HX-20). Three exact changes target the dispatch part:
  - `DS4_HW_FOLD`: the window's head kernel and its done flag become the first and last nodes of the window's expert graph, so a window is one graph launch instead of three submissions. Per-request arguments come through a small ring.
  - `DS4_HW_HEADQ8`: the head rounds the activation rows to int8 as it copies them, so the graph launches no separate quantise kernel.
  - `DS4_HW_PUBT`: for windows of 2–16 rows (verify, batch), the helper request is published by the routing launch's last block instead of a separate kernel.

## Prediction
- With FLAGFUSE (HX-21) already on: FOLD + HEADQ8 add −0.10 to −0.25 ms a token at B1; PUBT = PUBFUSE at B1 and −0.08 to −0.30 ms a step at B 2–8.
- In the build-12 stack: F + LP + HW −0.85 to −1.25 ms vs off (central −1.02); disproved if HW adds less than −0.05 over F + LP (then the helper windows are not on the B1 path once FLAGFUSE is in).
- Pre-registered: yes, in the build-12 run script, committed before the run. The levers' own A/B (each flag alone, a window trace) was written but not run.

## Correctness
- All three are bit-identical by construction: the same kernels with the same arguments in the same order (FOLD); the head's rounding uses the quantise kernel's own expressions (HEADQ8); the publish writes the same bytes with the sequence word last (PUBT).
- Load-time checks: HEADQ8 is compared with the quantise kernel byte for byte on every MI50 (16 rows, edge values incl. NaN, inf, denormals, signed zero); PUBT runs inside the routing check at 3 and 16 rows. All passed (MEASURED).
- End to end, the F+LP+HW stack is IDENTICAL to off on plain decode, drafter decode (greedy) and batch-test B 1/2/8 (MEASURED).

## Timing
- Hardware: 4 × RX 7900 XTX (XTX #1–3 Gen4 x16, XTX #4 Gen4 x8) + 4 × MI50 32 GB at 135 W (Gen4 x4 each). XTX at minimum power cap with −50 mV. MI50 DPM `high` (CP-03).
- Software: ROCm 7.14 on Linux; Strata v0.2.9 plus this fork's changes (the build-12 binary, SV-09).
- Measured only as a step in the build-12 stack: B1 plain decode, 64-token prompt, 256 tokens, drafter off, 3 interleaved reps.

## Verdict
- **The three levers together saved 0.08 ms a token**, separable from the rep spread (the ranges do not overlap), but below the −0.10 to −0.25 predicted. They are exact and stay in build 12.
- Their share could not be split: no arm ran a single flag, and the window trace that would show 7 → 5 dispatches a window was not run.
- **At B8 nothing showed** (one run a side): the predicted −0.08 to −0.30 from PUBT is not visible.
- Our reading [I]: once FLAGFUSE has moved the helpers' flag earlier, the remaining lateness of a one-expert window is mostly expert maths, not dispatch. That is the slice HX-23 aimed at.
