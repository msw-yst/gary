# FG-20: The BF16 matvec, re-scheduled for bandwidth (`DS4_BF16MV`): bit-identical, 0.51× the kernel time, 4 served users +9.8 % on the native MXFP4 pack
Status: kept (opt-in, release 4) · Date: 2026-11-17 (addendum 2026-11-19)
Code: in Gary's release commit (release 4): `src/dsv41/ds4_bf16mv.cuh` (new; the old kernel moved here unchanged, plus `bf16_mv2_kernel`), `src/dsv41/ds4_gguf.cu` (dispatch); bench `tests/dsv41/bf16mv_bench.cpp` (target `ds4_bf16mv_bench`). Flags: `DS4_BF16MV` (unset or `0`: the old kernel; `1`: variant `r1u4`; or a variant name `r1u2 r1u4 r1u8 r2u2 r2u4 r4u2 r1u4n r2u4n`). Measured served value: `DS4_BF16MV=r2u4n`.

## What and why
- On the native MXFP4 pack every dense matrix is BF16: the attention projections, the shared expert, the head and the Engram projection. On the 2.25-bit pack the same matrices are Q8_0 / Q5_K and go through other kernels, which is why this kernel never showed up in the 2.25-bit profiles.
- A kernel trace of native serving put the BF16 matvec at 13.1 ms of the lead XTX's 37.2 ms traced kernel time a step (35 %), 256 launches a step (MEASURED, traced). A first reading of that trace put the kernel at about 1 % of peak bandwidth; that used the 2.25-bit pack's byte counts. With the native pack's bytes it moves about 4.87 GB a verify step, about 370 GB/s, 39 % of peak (320–650 GB/s by shape) (INFERRED from the trace and the tensor shapes).
- The kernel is latency-bound, not broken: one warp a row, 16-byte vector loads, but each loop step issues one weight load a lane and waits for it before its FMAs, so a wave has one request in flight (INFERRED from the gfx1100 machine code).
- `bf16_mv2_kernel` keeps every lane's `fmaf` chain in the same order, the same butterfly reduction and the same epilogue, and changes only the load schedule: U steps of loads in flight, R rows a warp, optionally non-temporal loads. So the result is bit-identical by construction. With the switch unset, the old kernel runs; its machine code is instruction-identical to the previous build's on gfx1100 and gfx906 (REPORTED, from the build's disassembly check).

## Prediction
- Written before the run: the BF16 work a step about 12.5 → 6–7 ms; served verify step × 0.80–0.93; 4 users × 1.04–1.20.

## Correctness
- Bench, old kernel against every variant at the native pack's real shapes and edge shapes: BITWISE on all 16 A/B lines (MEASURED).
- Served greedy identity was UNINFORMATIVE: the server was not deterministic under the deterministic-cache settings used, so the repeat did not reproduce itself (MEASURED). Bit identity rests on the construction and the bench.

## Timing
- 17 Nov, the 4 XTX + 4 MI50 test machine, native MXFP4 pack, served with 4 slots and the drafter on. The same binary with the switch off (R0) and on (RX); cells 1 user 2K, 1 user 8K, 4 users 2K. Verify step from the engine log.

## Verdict
- **Kept, opt-in.** Bit-identical by construction and on every bench line; on native serving it takes about 2 ms off a verify step and adds about 10 % at 4 users.
- **The served step gain is smaller than predicted:** × 0.956 against × 0.80–0.93 (out). The 4-user gain is inside its band. The bench's one-row step time (0.89×) is closer to the served result than its 4-row figure (MEASURED).
- **The pre-registered verdict is INCONCLUSIVE** because of the control arms, not the switch: two runs of the native build without the change drafted 3.37–3.40 tokens a step against R0's 3.79 and drifted 10 % between themselves, so they are not like for like with R0. The same-binary R0 / RX comparison above is the evidence (MEASURED; the control arms' configuration difference is not yet diagnosed).
- On the 2.25-bit pack (build 17's served configuration) no effect is expected: its dense matrices are not BF16 (INFERRED; not measured).

## Reproduce
- `ds4_bf16mv_bench` (one GPU, no model): modes `ab` (old against each variant, bit for bit), `tm` (time per shape class), `step` (one decode step's launches), `roof` (read bandwidth).
- Served: a native MXFP4 pack with `DS4_BF16MV=r2u4n`; the engine prints one line naming the variant at start.

## Notes / caveats
- The measured binary was build 17 plus an MXFP4 kernel change, a measurement-only counter and this change. Release 4 adds this change alone on top of build 17; the BF16 matvec code and its dispatch are the same.
- One run an arm. The bench models 251 of the step's 256 launches (the five tiny ones are left out).
- The native MXFP4 pack is not the released serving configuration; the native build's other changes are not in this release.

## Addendum (2026-11-19): why the served greedy check was uninformative
- Expert placement differed between server starts (ME-13). With the placement frozen and its moves landing in fixed rounds, greedy outputs repeat 13 of 13 across starts. That is now the setting for served identity checks.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
