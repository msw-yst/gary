# FG-27: A kernel-gap trace of served decode on the 2.25-bit pack: one user waits on the other cards; four users wait on host sampling
Status: finding · Date: 2026-11-16
Code: in the fork's release commit (build 17, release 3; no code change). The trace analysis scripts are held privately. Flags: none (build 17's served environment, 4 slots).

## What and why
- Where does served decode time go on the lead XTX, between kernels as well as inside them? FG-15 traced one-row decode with the batch test; this traces the served engine, drafter on, at one and four users, to choose the next fusions.
- The same method on the native MXFP4 pack is FG-20's trace (the BF16 matvec finding) and FG-21 (the lead's waits). This card is the 2.25-bit pack.

## Prediction
- Pre-registered: yes. 1 user 2K, untraced: 8.5 ms a token [7.5, 9.8]; tokens a step 1.95 [1.5, 2.5]; tracer inflation 1.6 [1.15, 2.4]; lead launches a step 1,070 [900, 1,300]; lead idle 22 % [14, 32]; **host-bound share of the lead's idle 60 % [35, 85]**; fusion ceiling 3.7 ms a step [2.2, 5.5]; bandwidth-bound minimum 45 % of lead kernel time [25, 70].

## Correctness
- Measurement only; no output check. In every cell the trace's burst of lead kernels matched the client's request marks (4.0 / 4.1 s, 13.6 / 13.8 s, ...) (MEASURED).

## Timing
- 16 Nov, the 4 XTX + 4 MI50 test machine, build 17 served with 4 slots, the 2.25-bit pack. Cells: 1 user 2K (2 reps), 1 user 8K (2 reps), 4 users 2K (1 rep); 64 tokens a request. Arms: untraced U1, traced K (rocprofv3 kernel trace), untraced U2. A counter arm (P) gave no data.
- Three attempts. The first wrote no trace: stopping the server killed the engine before the tracer flushed, and the counter collection hung (NO DATA). The second wrote the trace (1.5 million rows), but the analysis found decode steps in only 1 of 5 cells. An offline re-analysis of that same trace (a step = one main forward plus the drafter forward; spans over 2× the cell's median left out) read all 5 cells.

## Verdict
- **One user: the lead XTX is 75–79 % busy, and its idle is mostly waiting for the other cards (cross-GPU all-reduce and helper joins), not the host.** The host-bound share was predicted at 60 % and measured at 18 %. Fusing the lead's kernels cannot recover a wait for another card.
- **Four users: about 71 % of the lead's idle is host-side per-row sampling and bookkeeping** (7.87 + 3.95 ms a step). At the time that was the biggest lever found; batching the sampler was built and tested on the native pack (FG-24) and gave no measurable gain there.
- The trace's own fusion ceiling (4 ms a step, mostly in attention) rests on estimated inside-kernel savings, because the counter arm failed. Later launch-fusion pricing (FG-32, FG-34) puts a removed launch at about 3.8 µs, so we read this ceiling as an upper bound, not a plan.

## Reproduce
- Served build 17 under `rocprofv3 --kernel-trace`, with the server stopped by SIGTERM to the engine first so the tracer can flush. The step segmentation script is not published.

## Notes / caveats
- The untraced 1 user 2K figure (13.5 ms a token) is much slower than served build 17 elsewhere (SV-17); the first rep of each cell was slow in every arm (16.1 ms at 2K), and this run made only 64 tokens a request, so drafting had little time to settle (1.19 tokens a step). Shares within the trace are the result, not the absolute speed.
- Traced figures are inflated 1.5–1.8×; untraced step splits are proportional estimates.
- One traced rep a cell.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
