# SV-25: Release candidate r2a (the stack build with `DS4_BF16MV` on) ships: exact, one user 15 % faster a token, 4–8 users 15–17 % more; r2b (attention split) held
Status: kept (r2a: release-gate verdict SHIP; r2b: held, its quality check unresolved) · Date: 2026-11-21
Code: not in the release commit of Gary, our fork of Strata (internal branches only). r2a = the stack build (SV-18) + the BF16 matvec of FG-20, on by default (`DS4_BF16MV=0` turns it off). r2b = r2a + `DS4_ATTN_SPLIT` on by default (QA-21). Flags: the stack's served environment (SV-18), five MI50 helpers, all MI50s at DPM `high`.

## What and why
- The BF16 matvec (FG-20) is bit-identical and made native serving faster in its own run, but was opt-in. r2a turns it on by default in the stack build; r2b adds a split attention kernel on top. The release gate asks: is r2a exact against the stack build, and no slower in any served cell, with a one-user gain of at least 0.6 ms a token?
- Decision (21 Nov): ship r2a first; hold r2b even if its own quality check passes, because the attention split on by default also changes the drafter's 2–5-token verify windows and turns off two kernel paths, which that check (single-token steps) did not cover.

## Prediction
- r2a: one-user decode −0.94 to −1.26 ms a token (from the bench at bench context); gate bar ≤ −0.6 ms, no cell slower by more than max(noise, 1 %), output identical. Pre-registered: yes.
- r2b: a teacher-forced quality check at 1–4-token windows must PASS before its own release gate may run. Pre-registered: yes.

## Correctness
- **r2a: ids EQUAL over 4,000 greedy tokens against the stack build** (one-shot run each, locked placement) (MEASURED).
- **r2b: UNRESOLVED.** The first quality run stopped with no data for the split arm: the split on by default broke the `DS4_ATTN_MERGE=3` load check; rc2 skips that check when the split is on (MEASURED / REPORTED). The second run (both arms at `DS4_ATTN_MERGE=2`, 12 prompts, 2,900 positions, against the hosted model's top-20, windows of 1–4 tokens): split engaged (160 launches a window), controls identical to each other; split against control KL −0.00024 [−0.00050, +0.00003] (bar +0.001: met), top-1 +0.07 pp [−0.62, +0.76] (lower bound below the −0.3 pp bar: not proven); top-1 lost at 30 positions, gained at 32 (MEASURED). Window 1 PASS, windows 2–4 unresolved.

## Timing
- r2a gate: 21 Nov, 18:43–20:47 UTC, the test machine with four XTX and five MI50 helpers, all five MI50s pinned to DPM `high` (confirmed in every server), native MXFP4 pack, served as released (live expert cache), drafter on; arms A (stack build) and B (r2a) in the order A1 B1 B2 A2 for each of the 4-slot and 8-slot servers. Noise = the larger difference between the two starts of one arm.
- r2b quality: 21 Nov 21:18 to 22 Nov 00:42 UTC.

## Verdict
- **r2a ships: exact, faster in every decode cell, no prompt-speed cost.** One user is 14–15 % faster a token (8.1–8.3 ms, about 120–124 tok/s) and 4 and 8 users get 15–17 % more throughput. The gain (−1.29 ms) is at the top of the bench prediction: on the served machine a decode step is about 9.5 ms, so a ~1.3 ms attention saving is a larger share than at bench context (INFERRED).
- **r2b is held, and deprioritised.** Its quality check could not bound top-1 to 0.3 pp with 2,900 positions, so its release gate refused under its pre-registration; KL is if anything slightly better. A separate study predicts a served gain of only −0.15 to −0.35 ms a token for it (INFERRED). A larger quality run only if that gain is shown to be worth it.

## Reproduce
- No published run: r2a and the served harness are not in the published release. `DS4_BF16MV` itself is in release 4 (FG-20).

## Notes / caveats
- **Freezes seen in passing, cells unaffected:** the stack build's one-shot exactness run took 100.4 s to read its prompt against r2a's 10.1 s (a prompt-read freeze in the control, not a property of r2a), and two 8-slot servers logged 31.5 s and 79.0 s of GPU memory eviction without moving their cells (MEASURED). The freezes are being investigated separately.
- Two starts an arm a server size; the 4-user cell's noise (3.45 tok/s) is the largest.
- The 400 ms rule excludes stalls that overlap another request's prompt read.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
