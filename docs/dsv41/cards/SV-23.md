# SV-23: Serving the native MXFP4 pack: ~82 tok/s for one user (faster than predicted), slow prompts, and output that moves with the live expert cache; native 4-bit stays the product
Status: served (the native build served from 16 Nov; decision 20 Nov: native 4-bit is the product) · Date: 2026-11-16
Code: not in the fork's release commit (the native build: internal build `nat18-r1`, commit d2a73071 = build 17 + the MXFP4 lookup fix + an expert counter). The first speed run used build 17 (internal build `deploy17`, commit 17d274cd) on the native pack. Flags: build 17's recommended environment, `--mmap-experts on`; the prompt helper could not be enabled on the native pack (no room on the MI50s).

## What and why
- The 2.25-bit pack, not the engine, is the distance to the hosted model; the native MXFP4 pack closes 88 % of it (QA-11). The question: is native 4-bit usable served on the test machine, at what speed, and is the native build's output stable?
- The native pack's routed experts are about 289 GB (REPORTED); 12,688 of them, 238.9 GB, do not fit on the GPUs and are read from host RAM and SSD by a CPU lane (MEASURED from the load lines).

## Prediction
- Native, one user × 2K: 15.4–25 ms a token (40–65 tok/s); first token 2K 4–12 s, 8K 16–50 s, 32K 65–240 s; 4 users 55–110 tok/s, 8 users 65–130. A third arm (experts copied into RAM instead of memory-mapped): × 0.9–1.05 of the memory-mapped arm. Pre-registered: yes.

## Correctness
- **The MXFP4 lookup fix in the native build is bit-identical:** 36 of 36 kernel A/B lines BITWISE on both card types, and faster in every timed cell (MEASURED).
- **The native build's served identity gate was uninformative.** Build 17 on the native pack did not reproduce itself run to run: a repeat of the reference differed on 2 of 3 prompts, so no comparison against it could pass (MEASURED). The cause was traced to the live expert cache moving experts between XTX memory, the MI50s and the CPU lane while serving: the same prompt can meet a different placement and give different output (INFERRED from the engine logs). Decision (16 Nov): serve the native build on the strength of the kernel fix's bitwise proof, and run identity checks with the cache's test settings (`DS4_CACHE_DET=1 DS4_SETTLE_IDLE=0 DS4_LAST_WINDOW=1`) from then on (ME-16).

## Timing
- 16 Nov, 13:23–14:09 UTC (speed) and 18:44–19:10 (native build gate, then served until 17 Nov 02:32), 4 XTX + 4 MI50 at 135 W, served, 4 then 8 slots, sampled requests, drafter on. Arm A: 2.25-bit pack (control); arm B: native pack, memory-mapped experts; arm C: native, copied in.

## Verdict
- **Native 4-bit serves at about 82 tok/s for one user: two-thirds of the 2.25-bit speed, and faster than predicted.** Prompts read 3–9 × slower (with no prompt helper, every read streams the CPU lane's experts), several users get 0.62 ×, and the machine is at its RAM limit.
- **The MXFP4 kernel fix barely moves served decode** (2K 12.12 → 12.08 ms, 8K 11.17 → 10.65): the expert kernels are not what limits native serving.
- **Decision (20 Nov): native 4-bit stays the product.** On the two agent tasks where the 2.25-bit pack failed, native passed at the hosted model's rate (native 4 of 6, hosted 4 of 7, 2.25-bit 1 of 7; REPORTED from the agent runs). Speed work goes into serving it (SV-24, SV-18). An all-IQ3_XXS pack was shelved: the CPU lane is only about 3 % of decode.

## Reproduce
- No published run: the native build and the served harness are not in the published release. Serve the native MXFP4 pack with build 17 and `--mmap-experts on`.

## Notes / caveats
- The drafter looked broken on native at first (18 of 1,554 steps drafted in arm B). That count covered the batched path only; one user drafts about 2.8 tokens a step (REPORTED).
- GPU busy read 0 % in arm B: a sampler artefact (the lead drew 96 W).
- Three reps a cell (two at 8K); one start per arm.
