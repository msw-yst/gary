# PF-23: A bounded replay for the second half of a prompt read (`DS4_YOCO=2`, the approach in delphi.cpp): slower at 1K, 2K and 14K, NO-GO; and what else the desk study found
Status: dropped (NO-GO; mode 1 stays) · Date: 2026-11-20
Code: `DS4_YOCO=2` was already in Gary, default off and never gated; no new code. Measured on the internal native build with STACK's configuration (SV-18).

## What and why
- A desk study compared Gary with delphi.cpp, an MIT-licensed llama.cpp-based engine for this model. Its headline prompt trick, cutting the second half of the layers (21–40) to a short window of rows during a prompt read, is something Gary already does: the long-prompt skip, on by default, cuts at the same layer. The difference is how many rows each keeps:
  - Gary's default (mode 1) keeps the exact receptive field, 2,668 rows, so it is exact and does nothing below about 3.7K tokens;
  - delphi keeps only the last window, about 128 rows, which is approximate. Gary already had that as `DS4_YOCO=2`.
- The desk ESTIMATE (INFERRED) was a 2K first token of 1.7–2.4 s instead of 2.9 s, on the assumption that prompt time is proportional to rows × layers.

## Prediction

## Verdict
- **NO-GO.** Mode 2 is slower at 1K, 2K and 14K and faster only at 4K. The desk estimate was wrong in sign at 2K. Quality is not the issue: it is equal.
- The 1K control, where neither mode skips anything, is 45 % slower in mode 2: mode 2 costs something on every prompt beyond the replay itself. That is unexplained, and worth a look before any retry.
