# Update, 14 Nov 2026: what we measured today

Our test machine: 4× RX 7900 XTX + 4× MI50 (MI50s at 135 W). Model: DeepSeek V4.1 Flash, our quant (about 2.25 bits a
weight). Every number below is MEASURED (read from a run's own output) unless it says ESTIMATE. Your machine will differ.

**In this release: build 16.** Measured today but **not** in this release: the batched-path fusion (`DS4_BT_FUSE=1`)
and the cache fix that keeps promotion (`DS4_ECOWN=1`). Measured together, they are the candidate for the next build
(section 7).

## In short

- Build 16 is faster than build 15 for long prompts (32K first token −18 %) and for several users (+2 to +4 %).
- It is **slower for one user**: 5 % (2K) to 9 % (8K) per token, and 15 % on the 8K first token.
- We found why. Build 16's correctness fix for the expert cache (`DS4_EC_FIX=1`) also stops the cache moving hot
  experts into XTX memory after a prompt. Build 15 was faster because it moved them, but it then counted some experts
  twice, so its batched output was wrong.
- A proper fix (`DS4_ECOWN=1`, not in this release) counts each expert once and keeps the move. Its output is identical
  to build 16's. It wins back the prompt-time loss, but only a little of the decode loss.
- The batched-path fusion (`DS4_BT_FUSE=1`, not in this release) is exact and gives +6 % with 8 users.
- Both together, against build 16 (not in this release yet): **8 users +12.5 %**, 4 users +5.3 %, and one user's 8K
  first token −12.5 %. Output identical, zero double counts.

## 1. Build 15 vs build 16, served, same day

One server at a time, alternating rounds (15, 16, 16, 15), so drift between rounds shows up. Sampled requests, drafter on,
4 slots (8 for the 8-user row). Served output with greedy sampling was identical between the builds.

| | build 15 | build 16 | change |
|---|---|---|---|
| 1 user × 2K: ms a token | 8.05 | 8.47 | +5.3 % (slower) |
| 1 user × 8K: ms a token | 8.68 | 9.44 | +8.7 % (slower) |
| 1 user × 2K: first token | 2.23 s | 2.32 s | +4.2 % |
| 1 user × 8K: first token | 5.87 s | 6.74 s | +14.8 % |
| 1 user × 32K cold: first token | 22.39 s | 18.30 s | **−18.3 %** |
| 4 users: total tok/s | 148.9 | 152.3 | +2.2 % |
| 8 users: total tok/s | 182.7 | 189.0 | +3.5 % |

Every change is larger than the spread between same-build rounds.

In one process (no server), build 16's five changes are worth −0.44 ms a token (12.89 → 12.47 ms, 77.3 → 80.0 tok/s).
Switching off each decode change in turn costs +0.15 to +0.17 ms. So the served single-user loss is not from those.
Details: [SV-16](cards/SV-16.md).

## 2. Why one user got slower: the cache fix

Same build 16 server, alternating rounds, with only `DS4_EC_FIX=1` switched on or off:

| one user | fix on (build 16) | fix off | change with it off |
|---|---|---|---|
| 2K: ms a token | 8.39 | 8.01 | −4.6 % |
| 8K: ms a token | 9.43 | 8.64 | −8.4 % |
| 8K: first token | 6.73 s | 5.89 s | −12.4 % |
| 2K: first token | 2.31 s | 2.22 s | −4.0 % |
| 4 users: total tok/s | 153.1 | 152.4 | no difference |

A short probe counted the cache's moves: with the fix on, 0 experts moved after a prompt; with it off, 20 (8 after a 2K
prompt, 12 after a 6.5K one). So build 15's single-user speed came from those moves. All three predictions we wrote
down before the run came in.

The fix stays in build 16. Without it, a moved expert is computed on both an XTX and an MI50 and added twice (4.9 % of
picks after 53 prompts), and batched output stops matching single requests ([HX-28](cards/HX-28.md)).

## 3. A fix that keeps the move: `DS4_ECOWN=1` (not in this release)

When the cache moves an expert from an MI50 into XTX memory, the request sent to the MI50 now carries a mark for each
expert the XTX already holds. The MI50 skips those, and the XTX does not wait for them or add them. Both sides read the
same table for each step, so there is no race. It is a small change, off by default.

Checks, in order; any failure would have stopped the run:

| check | result |
|---|---|
| flag off: output identical to build 16 (short prompts, drafter on and off, batch test, 32K, 110K, one served user) | PASS |
| flag on, expert cache off: output identical to build 16 | PASS |
| flag on, cache on, served: experts counted twice | **0 of 2.92 million picks**, with 926 cache moves |
| batch vs single requests, cache on (a test mode that fixes when moves land) | PASS: batches of 1, 2 and 8 all identical |

Served speed against build 16, alternating rounds:

| | build 16 | with `DS4_ECOWN=1` | change |
|---|---|---|---|
| 1 user × 8K: first token | 6.71 s | 5.88 s | **−12.5 %** |
| 1 user × 2K: first token | 2.32 s | 2.22 s | −4.3 % |
| 1 user × 8K: ms a token | 9.42 | 9.23 | −2.0 % |
| 1 user × 2K: ms a token | 8.39 | 8.44 | +0.6 % |
| 1 user × 32K cold: first token | 18.22 s | 18.71 s | +2.7 % |
| 4 users: total tok/s | 151.9 | 153.6 | +1.1 % |
| 8 users: total tok/s | 186.6 | 189.3 | +1.4 % (inside noise) |

4 of the 5 predictions came in. The prompt-time loss is fully recovered. Most of the decode gain in section 2 did not
come back. Our reading (ESTIMATE): part of build 15's decode speed came from the wrong, double-counted sum, not from
real work saved.

The 32K cold read got 2.7 % slower. Disk is ruled out: a cold-read probe read 0 MB from disk, with 0 major page
faults, in both builds (MEASURED). The prompt read itself is only 55 ms slower (17,860 against 17,806 ms), while the new
build makes 15 cache moves after it, against 0 for build 16 (MEASURED). That fits our suspect, the cache's settle step
after a prompt: it can take up to 800 ms and counts in first-token time. Not yet proven (ESTIMATE).

## 4. The batched-path fusion: `DS4_BT_FUSE=1` (not in this release)

Most served decode steps are batched, and the batched attention path lacked the fusions the one-row path already had.
This brings them over ([FG-16](cards/FG-16.md), item 2).

- Output identical everywhere: batch test B = 1 / 2 / 8 against single runs, and served greedy output with 4 users at
  once, 8 of 8, twice.
- Batched step, B = 1: 14.48 → 13.61 ms (−6.0 %). B = 8: 38.13 → 35.90 ms (−5.8 %). That is about 2.5 × what we predicted.
- Served: 4 users 153.5 → 159.7 tok/s (+4.0 %); **8 users 188.5 → 200.5 tok/s (+6.4 %)**; one user unchanged (it takes
  the one-row path).

## 5. How speed scales with cards

Single process, build 16, one cold run per setup, so differences of a few per cent are noise. Decode in tok/s with the
drafter off / on; cold prompt read for 2K / 8K tokens.

| XTX + MI50 | no drafter | drafter | 2K | 8K |
|---|---|---|---|---|
| 1 + 0 | 25.2 | 21.8 | 9.9 s | 21.5 s |
| 1 + 4 | 51.7 | 59.5 | 9.2 s | 20.9 s |
| 2 + 0 | 32.9 | 31.5 | 5.5 s | 8.7 s |
| 2 + 4 | 64.4 | 73.0 | 4.7 s | 7.9 s |
| 3 + 0 | 44.3 | 44.2 | 3.9 s | 6.9 s |
| 3 + 4 | 72.1 | 92.0 | 1.75 s | 6.8 s |
| 4 + 0 | 53.8 | 55.0 | 4.2 s | 6.3 s |
| 4 + 4 | 79.7 | 110.5 | 1.40 s | 5.2 s |

- Each MI50 adds decode speed until no experts are left in host RAM.
- The drafter needs the experts on GPUs. With no MI50 it is no faster, or slower; with all 8 cards it adds 39 %.
- Short prompts drop sharply once the MI50s have room for the prompt helper's buffers (about 1.3 GB each). With 4 XTX
  that is from 3 MI50s; with 3 XTX only at 4.
- 2 XTX + 1 MI50 reads prompts slowly and erratically (2K in 5.7 s, then 10.5 s on a re-run). Decode there is normal.
  We don't know why yet.

The full grid (every count of 1 to 4 XTX × 0 to 4 MI50) and the script are in
[benchmarking-gpu-permutations.md](benchmarking-gpu-permutations.md). Through the server, one user on 4 + 4 gets about
120 tok/s.

## 6. What did not work

- **Batching the MI50 helper's decode window, twice.** First one persistent launch per window, then a hybrid that keeps
  today's kernels for live work. Both were exact, and both removed the cost of empty windows (−33 to −39 µs). But both
  were slower once two or more experts are active in a window (up to +34 µs for the hybrid). Not shipped. The first
  attempt's "output differs" result turned out to be a fault in our test bench, not in the kernel.
- **Pinning the MI50s' PCIe link speed.** No difference served (−1.1 % against 8.2 % noise). The links already hold
  their speed. Dropped.
- **A published DFlash drafter for DeepSeek V4 Flash.** It was trained for V4, not V4.1: different width, layer count
  and expert count. It would need retraining. Our drafter stays DSpark, DeepSeek's own, shipped with the V4.1 checkpoint.

## 7. Next

- **The next build, measured:** build 16 + `DS4_BT_FUSE=1` + `DS4_ECOWN=1`, against build 16, same day, alternating
  rounds. Identity checks passed first, with zero double counts. Not in this release yet; it is the candidate for the
  next build. All MEASURED:
  - 8 users: 180.3 → 202.8 tok/s (**+12.5 %**), 44.5 → 39.4 ms a token each. 8 users × 8K: +10.6 %, first token −10.6 %.
  - 4 users: 153.5 → 161.6 tok/s (+5.3 %).
  - 1 user: 8K first token 6.73 → 5.89 s (−12.5 %), 2K first token −4.7 %, 8K decode −1.9 %, 2K decode +0.7 %.
  - 32K cold first token: +3.0 %.
  - 7 of 9 predictions came in. The two misses were the 8-user cells, which came in better than predicted.
- **Swap instead of evict (design stage).** When the cache moves an expert from an MI50 up to an XTX, that expert's slot
  on the MI50 is no longer used. The cold expert pushed off the XTX can go into it, so the MI50 serves it instead of host
  RAM. Memory use on both sides stays the same. The handover has to be staged: copy first, then change the owner at a step
  boundary, so no expert is ever skipped or counted twice. Where it helps is a long-running server. With `DS4_ECOWN=1`, experts pushed off the XTXs
  slowly build up on the host-RAM path; the swap keeps that path empty. Expected (ESTIMATE): about 8 % faster 2K first token
  after 50 prompts. Fresh-server tests like ours can't see it. Decode barely changes.
- **One user is still slower than on build 15** (ESTIMATE, across two runs: about 5 % at 2K and 6 % at 8K with
  `DS4_ECOWN=1`). That is the open gap.
- **The 2 XTX + 1 MI50 prompt anomaly.**
