# PF-13: The MI50 prompt helper from 2K to 128K: never slower in one process, slower from 16K when served
Status: finding (helper slower from 16K when served; a length cap measured as predicted, and in build 16, this release) · Date: 2026-11-13 (addenda 2026-11-14, 2026-11-19, 2026-11-20)
Code: in Gary's release commit (build 15). Flags: `DS4_PF_HELPER=8192` with `DS4_PF_TILE=1` (on, as deployed) against `DS4_PF_HELPER=0` (off). A cap that turns the helper off above a prompt length (`DS4_PF_HELPER_MAXP`, code default unset) was built and measured afterwards; it is in build 16, this release, at `8192` in the recommended environment.

## What and why
- SV-14's served 32K time to first token with the prompt helper on (23.1 s) was slower than SV-11's helper-off run on the same cards (18.9 s), and the single-process prompt figures said the helper should be faster or equal at that length. Two runs located the difference.
- **Sweep (one process a prompt):** build 15, prompt read at 2K, 8K, 16K, 32K, 64K and 128K, helper on against off, cold, one process per prompt (2 reps at 2K / 8K / 32K, 1 rep at the others), then 128 decode tokens.
- **Served:** build 15 behind its server (4 slots), one user, cold distinct prompts 2K–64K, 2 reps a length, in three server lifetimes: on, off, on again (a drift control).

## Prediction
- Sweep: on faster at 2K and 8K, on faster or not separable at 16K, not separable from 32K, no crossover. A second, served hint (the off run faster from 8K) was written beside it as the alternative. Decode after the prompt unchanged (±0.3 ms). Pre-registered: yes, before the run.
- Served: helper slower from 16K, with on / off about 1.16 at 16K, 1.22 at 32K and 1.23 at 64K; 2K on / off 0.62; 8K 0.99. Pre-registered: yes, before the run.

## Correctness
- Not an identity run. The helper path is not bit-identical by design (PF-11); unset is.
- Both served arms placed the same experts in VRAM (6,826 of 15,744 a card) and the helpers held the same 8,918 experts, so placement does not explain the difference (MEASURED).

## Timing
- 13 Nov 21:56 (sweep) and 22:36 (served), after the hardware change (HW-09): 4 × RX 7900 XTX + 4 × MI50 at 135 W. Expert cache on, memory-mapped experts, drafter loaded off (sweep).

## Verdict
- **In one process the helper is never slower:** clearly faster at 2K and 8K, not separable from 16K to 128K, no crossover. The single-process prediction held; the served hint did not reproduce there.
- **Served, the helper is slower from 16K:** 2K on is 0.62 × off, 8K not separable, 16K 1.19 ×, 32K 1.21 ×, 64K 1.25 ×. The served prediction held; the crossover is between 8K and 16K.
- **Where the cost is:** served off (32K 18.4 s) matches single-process off (18.3 s), so the server itself adds nothing; the extra time is the helper path inside the server, with long per-card helper waits [I]. Off streams 86–383 GB from host RAM and is still faster.
- **What to run today:** served prompts of 8K or less with the helper on; above that, off is faster. Publishable served TTFT for build 15: 2K 2.9 s (on), 32K 18.4 s and 64K 35 s (off); build 16 gets these with the cap (32K 18.3 s served, SV-16). A cap that uses the helper only up to a prompt length was built after this run (predicted served 32K 22.2 → ~18.4 s, 64K 43.8 → ~35 s, 2K unchanged; measured on 14 Nov, see the addendum); it is in build 16.

## Reproduce
- No published run: the code is in the release commit; a scripted public re-run has not been prepared for this card.

## Notes / caveats
- The sweep's 16K, 64K and 128K points are one rep each; its noise figure comes from the 2-rep lengths.
- The served on-again control drifted +4–7 % against the first on run, under the 12.2 % noise used for the verdict.
- Why the served helper path is slower is not measured. The best reading so far [I]: per-layer helper work that grows with the chunk's rows (prompts over 8K are read in chunks of more than 4K rows), uneven load across the four helpers (1.26–1.43 ×), and the expert-cache leak of HX-26.

## Addendum (2026-11-14): the prompt-length cap measured (in build 16, this release)
- `DS4_PF_HELPER_MAXP=8192` keeps the helper for prompts up to 8,192 tokens and reads longer ones without it. Served (4 slots), one user, cold distinct prompts 2K–64K, 2 reps a length, against the deployed helper (ON); same expert placement in both servers.
- Identity: with the cap, a 4K prompt gave the helper-on tokens and a 24K prompt the helper-off tokens, token for token (MEASURED, helper-cap.txt).
- **Served first token, ON → cap: 2K 2.87 → 2.87 s; 8K 7.43 → 7.39; 16K 12.32 → 10.55 (−14 %); 32K 22.17 → 18.43 (−17 %); 64K 43.71 → 35.04 s (−20 %)**; decode unchanged (7.1–7.5 ms a token both). Every length landed where it was predicted (16K 10.45, 32K 18.4, 64K 35.0; 2K and 8K unchanged) (MEASURED, helper-cap.txt). Noise 11.6 %.
- So the cap takes long served prompts back to the helper-off times while short prompts keep the helper's 2K gain. Build 16 has the cap, and its recommended environment sets `DS4_PF_HELPER_MAXP=8192`. Without the cap, the same effect needs `DS4_PF_HELPER=0` for long-prompt workloads.

## Addendum (2026-11-19): the length cap on the native pack
- On the internal native build, the RAM-store fix of PF-19 sets this cap aside: past it, a read would stream the helpers' experts from the model files.
- With that store fix and DMA from the store, the helper is faster than production at 2K, 8K and about 14K on native (× 0.22, × 0.44, × 0.48 of production's first token; PF-20). Prompts longer than 14K were not measured there.
- On the 2.25-bit pack (this release) the cap stays as described above.

## Addendum (2026-11-20): keep the cap on the 2.25-bit pack
- The native pack's store switch (`DS4_STORE_UNHELD`) sets this cap aside on any pack. On the 2.25-bit pack that sends 32K reads through the helper again: 32K first token 17.8 → 23.5 s (MEASURED, PF-22). For the 2.25-bit pack, leave that switch off so the cap applies.
