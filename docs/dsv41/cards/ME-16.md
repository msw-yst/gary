# ME-16: Speed is measured with a live cache, as served; locked placement only for exactness
Status: method · Date: 2026-11-20
Code: no engine change for the rule. A candidate fix for the live first-token gap (`DS4_CACHE_PF_HOLD=1`) is coded on an internal branch and compiled; not yet run. Test-mode flags: `DS4_CACHE_DET`, `DS4_CACHE_FREEZE` (ME-13); `DS4_SETTLE_MS` (existing).

## What and why
- ME-13 introduced a locked placement mode for A/Bs: the expert cache's moves land in fixed rounds (`DS4_CACHE_DET=1`) and the placement is frozen after eight warm-up reads (`DS4_CACHE_FREEZE=8`). Greedy repeats then come back identical, which makes "bits differ" mean something. From 19 Nov most native A/Bs, including STACK (SV-18), were also timed in this mode.
- Neither switch is a serving setting. On 20 Nov we measured how far locked timing is from the configuration as served (SV-20).

## What we found
| finding | numbers | label |
|---|---|---|
| live decode is faster than locked | +6–9 % on every cell: one user 2K 107.5 against 101 tok/s, four users 119.2 against 109.0, eight users 151.2 against 139.3 | MEASURED (SV-20) |
| the live first token is slower by about a constant | 2K +0.68 s (3.62 against 2.94), 8K +0.49 s, 32K +0.6 s | MEASURED (SV-20) |
| the test mode without its freeze is not a speed | `DS4_CACHE_DET=1` alone waits for every live move: per-request decode split into 105–111 tok/s and 18–57 tok/s; that arm was discarded | MEASURED |
| a live arm's average can hide a cold start | a profiling arm in live mode read 390 ms a token on average; token 1 took about 70 s (the cache moved 450 experts from file-backed pages with about 8 GiB of RAM free) and one token 22 s; the median live token was 22 ms, the same as locked | MEASURED (FG-25) |

- **Why the first token is slower live (INFERRED, from reading the code; not yet tested).** At the end of each prompt read, before the first token is sampled, the cache runs swap rounds for up to 800 ms (`DS4_SETTLE_MS`); in locked mode that step returns at once. A fixed cost of up to 0.8 s fits a gap that is about the same at 2K, 8K and 32K better than contention during the read, which would grow with the prompt.
- **Why decode is faster live: not established.** A live cache keeps adapting the placement to the traffic; a frozen one keeps what it had after eight warm-up reads (INFERRED).

## The rule (from 20 Nov)
- **Headline and A/B speed numbers run live, as served:** no freeze, no deterministic-rounds waits. Warm up until the placement settles, interleave the arms (ABBA), use more repeats than a locked run needs, and report the placement drift.
- **Locked mode is for exactness only:** identity and "same output back to back" checks.
- **Report token 1 separately** in any live decode measurement, and mark a live speed valid only if no move lands in the timed window and no token in it exceeds five times the median.

## Sizing the next A/B to the question
- The test of the first-token fix was first planned at about 180–190 GPU minutes (two live rounds of every cell, plus long-context and many-user cells). For one switch that is out of proportion. It has been re-planned to a 30–40 minute target: a few minutes of locked exactness, then live arms ABBA with one warm server per arm, first token at 2K and 8K and one-user decode only; the many-user cells are added back only if one-user decode moves. A no-code check comes first: `DS4_SETTLE_MS=0` live against the default. Neither has run yet.

## Notes / caveats
- The 20 Nov cards say in their Timing line when they were timed locked; earlier native cards say "placement frozen" or "pinned" where they were. Ratios within a locked run stay valid; absolute speeds from it understate served decode.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
