# PF-26: A 16,384-token prompt chunk at tp3: 1 s slower, with fewer experts in VRAM
Status: dropped (not adopted; never re-tested at tp4) · Date: 2026-11-10 or earlier (exact day not recorded)
Code: in the fork's release commit (existing option, no new code). Flags: `--prefill-chunk 16384`.

## What and why
- Prompts are read in chunks. A larger chunk means fewer passes over the weights per prompt, so it should read long prompts faster, at the cost of larger chunk buffers in VRAM.

## Prediction
- None recorded. Pre-registered: no.

## Correctness
- Not run. A different chunk size batches prompt rows differently, so it is not expected to be bit-identical (INFERRED).

## Timing
- tp3 layout (three XTX), before build 11. Prompt length and reps not recorded in the sources we have.

## Results
| item | result | label |
|---|---|---|
| prompt time | about +1 s (slower) | REPORTED |
| Engram stage | 0.5 → 1.9 s | REPORTED |
| routed experts held in VRAM | 539 fewer | REPORTED |

## Verdict
- **Slower, and it costs VRAM: dropped.** The bigger chunk's buffers pushed 539 experts out of VRAM, and the Engram stage grew from 0.5 to 1.9 s, more than the saved passes gave back (INFERRED from the three figures).
- Never re-tested on the four-XTX layout. In the release, the default chunk is chosen once at load by a rule over byte counts (no timing); an explicit `--prefill-chunk` overrides it.

## Reproduce
- Launch with `--prefill-chunk 16384` against the default and time the same long prompt.
