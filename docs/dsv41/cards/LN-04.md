# LN-04: Placing experts by live counts (`DS4_PLACE`): −2.1 to −2.3 ms a token on the bench, not bit-identical
Status: open (quality pass and served A/B staged) · Date: 2026-11-22
Code: not in the release commit of Gary, our fork of Strata (internal branches only: a measurement build, and the same change on release candidate r2a). Flags: `DS4_PLACE=<counts file>` (default off: placement by the static profile).

## What and why
- LN-01 found the static profile a poor guide to which experts are hot live. `DS4_PLACE` places experts from a counts file instead. Does placing by live counts cut decode time, and do counts from served traffic work as well as counts from the same text?

## Prediction
- Pre-registered: yes. −1.0 to −2.5 ms a token; bar 0.300 ms.

## Correctness
- Null control: placing by the profile through `DS4_PLACE` is bit-identical to no flag (EXACT-NULL PASS) (MEASURED).
- Live counts change outputs from token 4: a different placement changes the order in which expert partial sums are added (EXPECTED; INFERRED). Quality not judged yet.

## Timing
- 22 Nov, the test machine (four XTX + five MI50 helpers), native MXFP4 pack, fixed placement, single user, drafter off, **sampled** decode, 2K prompt, 4,000 tokens. Arms: C (collect warm-up counts), R (reference), A1 B1 B2 A2 (A = profile, B = warm-up counts), S (counts collected from served traffic).

## Results
| item | result | label |
|---|---|---|
| A (profile) | 21.43 / 21.58 ms a token | MEASURED |
| B (warm-up counts) | 19.21 / 19.29 ms a token: **−2.258 ms (−10.5 %)**, noise 0.061 | MEASURED |
| S (served counts) | **−2.071 ms a token** | MEASURED |
| lane share of picks | A 0.1115 → B 0.0497 (S 0.0515) | MEASURED |
| lane experts a token / engine lane time | 26.8 → 11.9 / 5.4 → 2.5 ms | MEASURED |

## Verdict
- **Placement by live counts is a real decode win on the bench, ~10 %, and counts from served traffic work about as well as same-text counts.**
- Not shippable yet: outputs are not bit-identical, so it needs a teacher-forced quality pass; and this is a drafter-off bench with the lane at 11 % of picks, while the served box (drafter on, live cache) puts 0.5–2.2 % on the lane, so the served gain will be smaller (INFERRED).
- Staged next: a quality pass (three teacher-forced arms, ~204 GPU-min; an UNRESOLVED result is the likely outcome at this sample size, and how it counts must be decided first) and a served A/B with served counts (~72 GPU-min).

## Reproduce
- No published run: the code is not in the release commit.

## Notes / caveats
- Offline, counts from the bench text placed badly for served text (lane share 0.19), while served counts on served text gave 0.0065 (REPORTED): counts must come from the workload served.
- The C and R arms took heavy GPU evictions at load (HW-17; prompt reads 72 / 91 s); A, B and S were clean.
- The release candidate places the drafter layer's experts by index, not by hotness (INFERRED from source); unmeasured.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
