# DR-06: The drafter's cost model on live traffic, and acceptance by text type
Status: finding · Date: 2026-11-11
Code: in Gary's release commit (build 11 as deployed). Flags: drafter on, confidence 0.3, block 3; sampled requests (temperature 0.6, top-p 0.95, top-k 20). The adaptive-policy flag `DS4_DSPARK_ADAPT=1` is in Gary's release commit (default off; [DR-08](DR-08.md)).

## What and why
- The drafter is worth about a third of the served speed (SV-08), but its settings came from short greedy tests (DR-01). This card fits a cost model to the live requests of the SV-08 session, checks it against the measured time, and uses it to ask whether the policy can still gain.
- A drafter round: one draft call (the drafter always runs its full 5-row window; `--dspark-block` only truncates the list), then one trunk pass that verifies the kept drafts as extra rows.

## Prediction
- The model: ms a token = (D + S + c × drafts verified) / tokens a round, with D the draft call, S a one-row trunk pass, c the cost of each extra verify row.
- Pre-registered: no. The model was fitted after the session, and checked against a held measurement (the session's total time).

## Correctness
- Under sampling, the verify step keeps a draft with probability min(1, p/q), so drafted output is exact in distribution, not byte-identical to drafter-off. Any policy change alters only how many drafts are verified, never the keep rule.

## Timing
- Hardware: 4 × RX 7900 XTX (XTX #1–3 Gen4 x16, XTX #4 Gen4 x8) + 4 × MI50 32 GB at 135 W (Gen4 x4 each). XTX at minimum power cap with −50 mV. MI50 DPM `high` (CP-03).
- Software: ROCm 7.14 on Linux; Strata v0.2.9 plus Gary's changes (build 11), 131,072-token context.
- 50 requests with drafting, token-weighted mean context ~75K.

## Verdict
- **The model accounts for the measured decode time within 0.3 %.** A round at the live mean costs 2.4 + 15.5 + 1.85 × 3.11 ≈ 23.6 ms for 2.09 tokens.
- **A draft is worth verifying while the chance that it and all drafts before it are kept stays at or above c / (ms a token) = 3.11 / 11.47 ≈ 0.27** (0.25 in thinking, 0.32 in tool calls). On live traffic all three positions clear it, so the policy is near its optimum: block 2 would lose 0–3 %, block 4 is about break-even (−0.8 to +0.3 %). What is left for policy is about 0–3 % [I].
- **Text type matters more than any setting.** Tool calls and code-writing are predictable and run at ~103 tok/s; thinking prose runs at ~81 tok/s. Most generated tokens are thinking.
- **The big terms are not policy:** c is about a quarter of a round, and most of it is the extra row's routed experts and MI50 picks, not attention [I: two-row windows carry about twice the helper wait of one-row windows]. That makes the verify-row cost the largest single production lever: 3.1 → 2.0 ms a row would give about +8 % [I].
- **An adaptive policy (`DS4_DSPARK_ADAPT=1`) was built and tried** in the build-12 production phase at the served confidence and block. Length-matched it was equal to build 12 (SV-09). At the served cap it can only drop drafts.

## Reproduce
- The per-request "drafts N of M kept; per position (kept / reached)" and prompt lines are printed by any Strata server with the drafter on; fit S and c with D fixed.

## Notes / caveats
- The extract holds every request line of the session, including a short smoke request outside the 50 fitted, so its sums are slightly higher (48,231 tokens, 24,527 of 41,530 drafts kept).
- D and S are collinear on this traffic (almost every round drafts), so D was fixed at its measured value and S and c fitted.
- The text-type split uses each request's progress lines (the token at which thinking ended), which contain task text and are not published. Its boundaries are known to about ±40 tokens.
- All acceptance numbers are for sampled requests at temperature 0.6. Greedy agreement rates are higher and would overstate deep drafts.

## Addendum (2026-11-13): the verify-row cost measured directly, and where production time goes

- **c measured, not fitted.** A rows test on build 12 (11 Nov) gave one-to-six-row steps of 15.00 / 17.70 / 20.10 / 23.00 / 25.80 / 28.20 ms, so **c = 2.66 ms a row** (REPORTED from the run summary as read in the ledger). A teacher-forced run on build 13 (12 Nov, 8K context, one to four rows) gave 14.983 / 17.706 / 20.114 / 23.099 ms, **c = 2.697 ms a row**, inside its pre-registered 2.3–2.9 (MEASURED). Both are lower than the 3.11 ms fitted above on build 11: the builds since made rows cheaper. The extra row doubles the helper entries a step (62.1 → 123.7).
- **No stage breakdown yet.** The same run tried to split c into stages with a profiler, but the profiler's own cost changed with the row count (by more than its 0.3 ms bound), so every stage slope was "no data" (MEASURED). A separate trace put the MI50's share of the row small (helper wait +0.04, MI50 maths +0.07 ms, within noise) (REPORTED).
- **Production is mostly verify windows:** in the served production harness only 16 of 314 decode steps (5.1 %) are one-row steps (REPORTED, FG-08). One-row savings barely reach serving; c is still the largest production lever.
- **The host tail:** without the drafter the host's part of a step is 0.118 ms; with the drafter loaded it is 0.415 ms, so the drafter's host path owns most of it (MEASURED, verify-row-cost.txt).
- The policy itself was revisited on served traffic in DR-08.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
