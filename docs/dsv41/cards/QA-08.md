# QA-08: Output depends on which experts fit in VRAM: code size and context length are part of exactness
Status: finding (fix applied; a build-time check proposed) · Date: 2026-11-11
Code: the fix is a two-line `#if` in the gfx906 kernel file, not in the fork's release commit (internal branch only). Flags: —.

## What and why
- The first merged build-12 binary (SV-09) failed its identity gate: with every new flag off, its plain decode, drafter decode and batch-test all differed from build 11, from about token 22. Each flag had passed its own identity gate on its own branch.
- A bisect over the branches' binaries found the step that caused it and the mechanism. It is not a numeric bug in any kernel. It is a change in *which experts are held in XTX VRAM*.

## Prediction
- None: this was a diagnosis after a failed gate. Pre-registered: no.

## Correctness
- This card is about correctness itself. The facts below are MEASURED unless marked.
- **Default path vs build 11, by binary:** the helper-window branch, the loose-ends branch and the drafter branch were each IDENTICAL, with 7,177 experts in VRAM. The MI50-kernel branch on its own (HX-23) DIFFERED, with 7,176. So one branch alone reproduced it, with no merge involved.
- **Free VRAM at placement** (a diagnostic print in the placement step, outputs otherwise byte-identical): every XTX had exactly 2,097,152 B (2 MiB) less than under build 11. The tightest member then fits one routed expert fewer: 6,793 → 6,792 trunk experts, 7,177 → 7,176 in VRAM in all.
- **Why 2 MiB [I, consistent with every build measured]:** the GPU loader maps each code object in 2 MiB pieces. Build 11's gfx1100 code object for the expert-kernel source file had a loaded span of 12,570,001 B, only 12,911 B under 6 × 2 MiB. The new MI50 kernels are only ever launched on gfx906, but their 32 template instances were also emitted, with empty bodies, into the gfx1100 code object, which grew to 12,608,913 B and so took a seventh 2 MiB piece on every XTX.
- **Why one expert changes the output [I]:** the expert that no longer fits moves to an MI50 helper, which shifts the helpers' per-layer slots. Routed experts then run on different hardware with a different accumulation order, so some sums round differently.
- **The fix:** name the new kernels only in the gfx906 device pass. The gfx1100 code object went back to 12,570,001 B. The fixed binary was IDENTICAL to build 11 on plain decode, drafter decode and batch-test B 1/2/8, with 7,177 (decode) and 7,137 (batch-test) experts in VRAM, and with the MI50 kernels switched on (their engine counter non-zero) the output was IDENTICAL too.

## Verdict
- **On this engine, byte identity is a property of the expert placement as well as of the arithmetic.** Anything that changes free VRAM at load can change the output, with no bug anywhere:
  - code size: a code object crossing a 2 MiB boundary costs 2 MiB on every card;
  - context length: the KV cache is allocated before the experts. At a 262,144-token context each XTX holds 7,011 experts against 7,059 at 131,072 (QA-09), so a 256K server's outputs are not byte-comparable with a 128K server's [I];
  - any buffer a flag allocates at load. The flags in FG-07, HX-21, HX-22 and SV-09 were written to allocate nothing, or to allocate in both the on and off states, for this reason.
- **So an identity gate must compare at the same placement.** The runs here print "experts in VRAM" per process, and a mismatch in that line explains a DIFFER before any kernel is suspected.
- **The margin is small and will be hit again.** Build 11 had 12,911 B of headroom in that one code object. A CPU-only check after every build, comparing each gfx1100 code object's 2 MiB piece count with build 11's, is proposed and not yet in the repository.
- This is the same class of effect as QA-03 (a tuned GEMM changing summation order) and the expert-cache divergences in DR-01: near-ties resolving differently, not wrong arithmetic. Quality is not expected to move; the gate exists to catch real bugs, and this cause has to be ruled out first.

## Reproduce
- `llvm-readelf -l` on each gfx1100 code object of a build: the loaded span is the largest PT_LOAD end. Compare the 2 MiB piece count with the reference build's.

## Notes / caveats
- The 2 MiB mapping granularity is inferred from the measured 2,097,152 B drop and from every other build in the bisect: other code objects grew too but stayed within their piece count, and those builds stayed IDENTICAL.

## Addendum (2026-11-13): the code-object check in use
- The proposed check now runs on every build before any GPU time. In two days it stopped two builds before identity runs: the prompt-tile port would have grown an XTX code object from 6 to 7 pieces (fixed by compiling its kernels for gfx906 only, PF-12), and a fused MI50 kernel tripped a cruder rule (fat binary +1.38 MB) although every XTX bundle was unchanged; the rule was refined to accept MI50-only growth when every XTX bundle is byte-identical (HX-25) (REPORTED from the build logs).
- The headroom is small: one XTX code object of the main expert source file has 12,911 bytes left before its next 2 MiB piece, so new XTX kernels go into their own source file (FG-13) (REPORTED).
- A related trap: adding a kernel to that file changed how the compiler built an existing kernel instantiation, so ports now also compare the old kernels' machine code with the previous build (FG-14).
