# HW-05: An XTX's SMU stopped responding mid-sweep; the guard that followed
Status: incident (guard added) · Date: 2026-11-10
Code: not applicable. Flags: host tooling.

## What and why
- At 01:27Z, during HX-10's latency sweep, XTX #2's system management unit (SMU) stopped responding (driver log). The OS shutdown then hung for about 4 hours until a manual power cycle.

## Prediction
- No prediction was recorded before the run.
- Pre-registered: no.

## Correctness
- Not applicable.

## Timing
- Not applicable.

## Verdict
- Added: an SMU watchdog that detects the driver's SMU-failure messages and forces a hardware reboot, a hardware watchdog, and remote kernel logging. A dry run of the guard passed; its real-reboot path has not fired since.
- The driver log is not published (it carries identity lines).

## Reproduce
- Fork release commit with the flags above; a scripted public re-run has not been prepared for this card.

## Notes / caveats
- None beyond the above.

## Addendum (2026-11-13)
- The same card's SMU hung again on 12 Nov 04:31, at near-idle between runs (a DMA ring timeout, then the same "no response" message, card at about 30 °C, no PCIe errors). This time the watchdog matched the message and rebooted the host, as designed: its real-reboot path has now fired once (REPORTED from the driver and watchdog logs).
- On 13 Nov 13:09 the card hung a third time, with different wording ("SMU is in hanged state") that the watchdog's pattern did not match, and the host lost power seconds later. The card has been removed (HW-09).

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
