# FG-21: Where a native decode step goes: the lead XTX is not overloaded, it waits, mostly for the CPU lane
Status: finding · Date: 2026-11-17
Code: not in the release commit of Gary, our fork of Strata (the native build is internal). Measurement: a kernel trace of native serving and a desk reading of it; a settings run with a lane-skip timing oracle.

## What and why
- On the native MXFP4 pack a verify step took about 38–45 ms against about 23 ms on the 2.25-bit pack (REPORTED from the 4-bit plan; MEASURED 44.5 ms in the settings run below). Before spending on kernels, the step was traced and read: what does the lead XTX do, and what does it wait for?

## Prediction
- None as numbers; a diagnostic.

## Correctness
- The lane-skip oracle skips the CPU lane's experts, so its output is invalid by design; it is a timing bound only. The trace inflated wall time by 1.18× (MEASURED); shares, not absolute times, are used from it.

## Timing
- 17 Nov, the test machine: 4 × RX 7900 XTX (tensor-parallel 4) + 4 × MI50 helpers; native MXFP4 pack, internal native build, one user, 2K and 8K prompts. Kernel trace: 4 of 5 cells captured.

## Results
| measure | value | label |
|---|---|---|
| verify step, base | 44.5 ms; decode 11.62 ms a token | MEASURED |
| verify step with the CPU lane skipped (oracle, output invalid) | 36.4 ms (× 0.82); decode 9.33 ms a token | MEASURED |
| share of expert picks on the CPU lane | 0.5 % | MEASURED |
| lead XTX busy | about 80–85 % (idle 15–20 %) | MEASURED (traced) |
| lead kernel time a step | 37.2 ms traced: BF16 matvec 13.1 ms (35 %, FG-20), waiting on helper joins 8.3, all-reduce wait 3.4, sparse attention 1.9 | MEASURED (traced) |
| MI50s busy at 1 user, 8K | 48–52 % | MEASURED (traced) |
| lead-only and lead-skew time | about 15 ms (14–19) of a ~44 ms step; about 13 ms of it waiting for results only the lead collects | INFERRED (desk reading of the trace) |
| what the lead waits for | CPU-lane experts 8.0–10.6 ms (joined on the lead), MI50 joins 3.8–4.2, routing about 0.6, gather and sampler 1.2–1.4 | INFERRED (same) |
| MoE all-reduce | the lead arrives last 97–98 % of the time; peers wait 13–17 ms a step | INFERRED (same) |
| all-reduces a step | 80, through pinned host memory (P2P only for prompts), about 32 µs each after the last arrival | INFERRED (same) |
| 4 users | the host sampler about 10 ms a step traced | INFERRED (same) |

## Verdict
- **The lead and its peers each compute about 25.8 ms a step (traced); the rest is waiting.** The peers' "73 % busy" is mostly spinning in the all-reduce while the lead collects results only it can collect: the CPU lane's experts above all, then the MI50 joins.
- **The CPU lane costs about 8 ms a verify step while serving only 0.5 % of the picks.** That made the CPU lane, not kernels, the native decode lever (FG-22, FG-23), and moving those experts to GPUs the main direction.
- Ranked levers from the reading: the CPU lane off the critical path (8–10.6 ms); MI50 results pushed to all four XTX (1.5–2.2; built, slower: the P2P write-up); a GPU-chained sampler and drafter (1–2.5); batched GPU sampling at 4 users (5–7 ms predicted; measured no gain, FG-24) (INFERRED estimates at the time).
- A correction made the same morning: the drafter already runs split across all four XTX; only its seeding is lead-only.

## Reproduce
- No published run: the native build is not in a release.

## Notes / caveats
- The first reading of this trace put the BF16 matvec at 1 % of peak bandwidth; that used the 2.25-bit pack's byte counts. Corrected: about 39 % of peak (FG-20).

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
