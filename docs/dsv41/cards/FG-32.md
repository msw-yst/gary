# FG-32: HIP graph capture of the decode attention block: exact, but 35 % slower as built; with zero host cost it saves 0.3 ms a token; build-once is worth about 1 % served
Status: shelved (exact; slower as built; the build-once first slice is built, not run) · Date: 2026-11-21
Code: not in the fork's release commit. Internal builds `graphcap-r1` (d01c9451), `graphcap-r2` (5fda9005), `graphcap-r3` (771acd54), `graphcap-r4` (ad2f2d33), `graphcap-r5` (2fa53556), `graphcap-r6` (f55f7188, the 8K bench fix); build-once first slice `graph-r2` (7ef6032a). Flags: `DS4_GRAPH_ATTN=1` (each layer's decode attention as one HIP graph per card), `DS4_GRAPH_REFRESH=n` (rebuild a graph after at most n updates, default 64); `DS4_GRAPH_ONCE=1|2` (build-once all-reduce graphs); all default off.

## What and why
- Decode attention is ~10 ms a token of many small launches (FG-25, FG-29). If launch overhead were a large part of it, replaying each layer's attention block as a HIP graph would cut it. Phase A: capture each layer's attention block every token, update the graph's node arguments, replay.

## Prediction
- Phase A: faster by cutting launch overhead (no band recorded). After the second run the ceiling was set from the direct-mode gaps: ~3.7 µs × ~9 gaps a layer ≈ 1.35 ms a token a card (INFERRED).
- Sixth run: that per-card rebuilds landing in different windows cause the all-reduce wait (supported), and that rebuilding on all cards in the same window removes it (not supported).

## Correctness
- Graph mode against the direct reference: 2K ids 0–511 byte-identical (495 from graph windows), 8K identical; later runs 1,280 ids identical, 89,600–120,160 graphed passes, 0 fallbacks (MEASURED).
- The 8K runs of the fourth to sixth runs ended with an abort (rc 134) after 768 of 768 ids equal: decode exact, the abort was in the exit bench (see below).

## Timing
- 20–21 Nov, the test machine, 4 XTX + 5 MI50 helpers, the native MXFP4 pack on the stack build, frozen placement, greedy, drafter off, 1 user 2K and 8K; direct and graph in one process (ABBA).

The 8K abort (desk diagnosis, INFERRED from the argument log, the kernel log and the source): the exit bench replays layers in reverse order. A layer without its own indexer reads the card's shared top-k buffer; going backwards, a ratio-2 layer read the next layer's ratio-1 top-k (indices up to ~8,900 against a 6,145-row cache) and faulted. At 2K the indices stay in bounds. Not a decode bug; fixed in `graphcap-r6` (compiles; not run).

Build-once, priced from the measured floor (INFERRED):
- drafter off, single-token bench (20.45 ms a token): −0.05 to −0.36 ms a token (0.2–1.8 %), after the costs build-once adds (step-block reads, fixed-maximum grids, graph launch);
- served, one user (8.08 ms a token, drafter on, verify windows of 2–4 rows): ~0 for the single-token plan; −0.05 to −0.10 ms a token (0.6–1.2 %) if verify windows are covered too, for about 4–6 working days.

## Verdict
- **Graph replay is exact, and as built it is slower** (+35–39 %): re-capturing and updating every token moves ~14 ms a token onto the host, and the per-card rebuilds make every card wait at the all-reduce for whichever card is rebuilding. Aligning the rebuilds did not help; the rebuild cost itself is what everyone waits for.
- **With zero host cost, graphs are slightly faster on the GPU: −0.3 ms a token at 2K (about 7.5 µs a block of ~10 kernels).** That is consistent with FG-18's 0.4–0.9 µs a kernel. The ~3.7 µs dependent-kernel gap is not removed by graphs; removing launches by fusion saves the whole gap (FG-34).
- In direct mode the host already runs ~15 ms ahead of the GPU at one user, so launch cost is not the one-user bottleneck.
- **Build-once (device-side per-token arguments, no updates) is worth about 1 % served.** A first slice (`DS4_GRAPH_ONCE`: the all-reduce sites as build-once graphs with their sequence number read from device memory) is built and compiles; its exactness and speed package is staged, not run. Low priority.
