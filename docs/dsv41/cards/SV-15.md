# SV-15: Prompt reuse across agent turns: already built and serving
Status: finding (no new lever; the warm-turn and identity runs on 14 Nov: reuse 96 % served; a second identity run with the expert placement held fixed found reuse exact) · Date: 2026-11-13 (run 2026-11-14)
Code: existing (conversation slots and in-model checkpoints, SV-02; `STRATA_DS4_SLOT_KEEP`, `STRATA_DS4_SLOT_GB`). Flags: as served.

## What and why
- The idea: a 32K agent turn with 1K new tokens should not cost a full 32K prompt read. The desk study checked what the served build already does, against live traffic.

## Prediction
- More reuse (merging the earlier prefix store, more checkpoints, smarter matching): about 1 % of wall time on the live mix, range 0–2 %. A warm 32K + 1K turn on build 15: about 1.1 s (0.9–1.6 s) against 25.9 s cold. Pre-registered: yes, in the study note.

## Correctness
- The study expected reuse to be valid but perhaps not bit-identical to a cold read (a run's sums could depend on where it starts and how it is chunked). The identity test compares against a server with reuse off, greedy, with the expert cache off; run twice on 14 Nov (addendum). The second run, with the expert placement held fixed, found reuse bit-identical.

## Timing

## Verdict
- **Not a new lever: the served build already reuses 92 % of live prompt tokens.** The remaining time-to-first-token lever for agent turns is the per-read floor, not reuse.
- The served benchmark measures cold prompts only (SV-11), which overstates an agent turn's latency by about 20 × [I]. A warm-turn row and a reuse identity check are proposed. The open prompt-read hang (SV-12) had slots spilled to disk at the time; the warm-turn test at more than 4 sessions exercises that path.

## Reproduce
- No published run: the code is in the release commit; the identity and warm-turn clients are not published.

## Notes / caveats
- The persistent prefix store of SV-02 (GPU-tested on 8 Nov) does not occur in the build-15 source tree (REPORTED from the study's search); merging it would take 1–2 days and would matter mainly for surviving a crash.

## Addendum (2026-11-14): the warm-turn and identity runs (build 15)
- **Identity** (2 agents × 3 turns of ~6.3–6.6K tokens, greedy, expert cache off; reference = reuse off; arms "pin" and "on"): reuse works and is fast (turns 2–3 first token 1.0–1.1 s with reuse on, against 7.7–8.1 s for the reference), **but reused turns do not print the reference's tokens:** 4 of 6 turns differ with "pin" and 3 of 6 with "on" (MEASURED, slot-reuse.txt). One differing turn (A1 with reuse on) reused nothing, so not all of the difference comes from reuse itself [I]. The likely reading is different chunk boundaries giving different rounding, i.e. near-tie flips as in HX-26's addendum; that it is benign is not proven [I]. A later turn also reused the earlier prompt but not the reply after it (a small missed reuse), and the restart step hit the run's 1,500 s timeout (MEASURED). The script's verdict: NO DATA (timeout).
- **Second identity run (14 Nov, fixed placement): reuse is exact.** Four processes with the same expert placement (original, re-read, cold reuse, pinned): the control turns are identical across all four, and every reused turn prints exactly the tokens of a fresh read (MEASURED). The first run's differences came from the expert placement, which differed slightly between its processes (7,162 / 7,113 / 7,068 / 7,023 experts in VRAM per XTX), not from reuse (INFERRED from that difference; it is the only one between the runs).
- **Warm turns** (served, 4 slots, 4 sessions of ~32K, ~1K new tokens a turn): **95.6–96.9 % of every warm prompt was reused**; a 32K + ~1.4K turn's first token took **2.10 s with one user** (cold first turns 16.9–21.4 s) and 2.2–8.5 s with four at once, because prompt reads are serialised (MEASURED, slot-reuse.txt). Predicted 0.9–1.6 s: slower. The script's verdict printed NO DATA because the turns carried 1,409–1,530 new tokens, outside its 900–1,400 band; the numbers above are read from its per-turn lines.
- So: reuse is the big served win (92–97 % of prompt tokens), at about 2 s for a warm 32K turn; with the same expert placement it gives exactly the tokens of a fresh read. Two server processes that place experts differently can differ by near-tie flips, reuse or not.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
