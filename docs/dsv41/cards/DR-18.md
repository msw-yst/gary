# DR-18: Why batched drafts are accepted less: the drafter's memory goes stale in plain batch steps; fixed on a branch (`DS4_BT_SEED`), not yet measured
Status: explained (cause found in the code and confirmed from served logs; the fix is built and compile-checked on a branch, not run) · Date: 2026-11-22
Code: not in the release commit of Gary, our fork of Strata (internal branch only, on top of release candidate r2a). Flags: `DS4_BT_SEED=1` (refresh every user's drafter state in plain batch steps) or `DS4_BT_SEED=2` (a user with stale state offers no drafts until it is fresh again); `DS4_BT_SEEDLOG=1` prints fresh / stale counts. Default off.

## What and why
- In served runs, drafts made inside batched steps were kept only 30–63 % of the time, against 94–97 % for a user alone. This had been read as "batch acceptance is low", and it weighed against drafting with four users (DR-10).
- A desk study (22 Nov) compared the single-user and batched drafting paths in r2a's source, and read the served engine logs, to find the cause.

## Prediction
- None before the study. Pre-registered: no.

## Correctness
- **What the code shows:** each user's drafter keeps a small ring holding the trunk's state for its last few positions. A drafted step refreshes it; **a plain batch step does not** (the source says so in a comment). With drafting limited to three active users (`DS4_BATCH_DSPARK_MAX=3`), a four- or eight-user batch runs hundreds of plain steps. When users finish and three or fewer remain, they draft from a ring about 500 positions out of date. The original authors noted the effect in a code comment ("fewer accepted drafts... the output is exact either way") but it was never measured.
- **Output is not affected today:** drafts are only proposals, so stale drafts cost speed, not correctness.
- **The fix:** greedy output stays bit-identical by construction (the trunk is untouched; only the drafter's state and the number of drafts offered change). Sampled output stays exact in distribution, but is not bit-equal to today's, because different drafts are offered. Both trees compile; nothing has run on a GPU.
- The other suspects were ruled out by reading the code: the batched path uses the same confidence cut (0.3) and the same keep rule as the single-user path in the served configuration.

## Timing
- Desk study, 22 Nov, over served engine logs from 20–21 Nov (4 XTX + 5 MI50 helpers, native pack, sampled).

## Results
| run / cell | how the batch got there | drafts kept | label |
|---|---|---|---|
| 2 users, drafting from the first step (133 of 134 steps drafted) | ring always fresh | **1,510 of 1,586 = 95.2 %** | MEASURED (engine log) |
| 4 users, the tail after ~500 plain steps, rep 1 | ring stale | 12 of 32 = 38 % | MEASURED (engine log) |
| 4 users, the tail, rep 2 | ring stale | 8 of 27 = 30 % | MEASURED (engine log) |
| 4- and 8-user cells of the full-box served run | tails only | 131 of 344 = 38.1 %; 296 of 472 = 62.7 % | MEASURED (run summary) |
| release-gate 4- and 8-user cells on r2a | tails only (3–19 drafted steps of 504–1,531) | 10 of 18 … 40 of 96 | MEASURED (engine logs) |
| one user alone, same run | always fresh | 376–380 of 390–404 (94–97 %) | MEASURED (engine log) |

- The two-user cells include the ends of their answers and still keep 95 %, so "the tail text is harder to predict" is not the cause (INFERRED). The pooled four-user tails, 20 of 59 (34 %), are far from 95 % on any binomial test (INFERRED).
- The 62.7 % cell is higher because each drafted step refreshes a few rows of the ring, so later tail steps are partly fresh (INFERRED; `DS4_BT_SEEDLOG` would show it).

## Verdict
- **Explained: batched drafts are accepted less because the drafter drafts from stale state after plain batch steps, not because batches are harder to draft.** With fresh state, batched drafting keeps 95 %, the same as a single user.
- **What the fix is worth (INFERRED):** almost nothing in today's steady benchmarks, where only 3–19 of ~500–1,550 steps draft from stale state. It matters for staggered real traffic: after each drop from four users to three, the remaining users draft stale for ~128 positions, at about 99 tok/s, below plain decoding's ~117. With fresh state they would run at ~187.
- **It removes a blocker on drafting with four users:** DR-10's test had every user drafting from the start (fresh rings), so its low acceptance on the 2.25-bit pack is the pack's (DR-11), not this. On native, a desk estimate puts four users drafting at block 1 at ~165 against 136 tok/s (+22 %), if position 1 keeps ≥ 0.63 (INFERRED).
- Next: a frozen batch test of the three modes (unset, 1, 2) with a staggered job, then a served four-user cell with the counters on. Designed, not staged.

## Reproduce
- Not reproducible from the release: the switch is on an internal branch. The stale-ring effect itself can be seen on any release build by serving four or more users with `DS4_BATCH_DSPARK_MAX=3` and reading the kept / offered draft counts of the steps drafted after users finish.

## Notes / caveats
- The kept fractions are from engine logs read by the desk study; small counts in each tail.
- Mode 1 adds work to every plain batch step (it computes the drafter's input taps); its cost is not measured. Mode 2 costs nothing in plain steps.
- A batch profiling package for the per-row cost of batched windows was staged alongside (internal branch only); not run.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).

Sources: no published data extract for this card; the run summaries are held privately.
