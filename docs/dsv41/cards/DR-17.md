# DR-17: Where a drafted verify window's time goes on release candidate r2a: an extra row costs about 3.2 ms, mostly experts on the CPU lane; a measuring package is staged
Status: desk (two desk studies; the measuring package is staged, not run) · Date: 2026-11-21
Code: none (desk study). The staged package uses release candidate r2a and an instrumented build (LN-01), both internal branches only. Flags: none new.

## What and why
- On the native pack the drafter is no longer the limit: at block 3 a single user keeps 92–97 % of drafts and a round lands 3.84–3.88 of a possible 4 tokens (MEASURED, served runs on the stack build and r2a).
- Every place where drafting lost money lost it on the **cost of a verify row**: four users drafting (DR-10), tree drafting (DR-13), DSpine-style long windows (DR-15, DR-16), and block 6 at several users (DR-12, which was a gate that could not see it).
- No run had ever split a verify row into stages: every stage-timing run was drafter-off, and the stage instruments only stamp one-row steps. Two desk studies (21 Nov) asked what a row is made of on r2a, what would move it, and how to measure it.

## Prediction
- Desk predictions for the staged package (not run): frozen row cost c 2.5–3.8 ms; the CPU lane's experts in a 4-row window ≥ 3× a one-row step's; block 6 over block 3 on r2a, one user: × 0.85–0.88 at 2K and × 0.86–0.92 at 8K; four and two users × 0.99–1.01. Pre-registered: yes, in the package (not yet run).

## Correctness
- Not applicable (desk). The package's exactness checks: in the frozen part, an instrumented 4-row arm must match an uninstrumented one bit for bit; in the served part, block 6's greedy output must equal block 3's (the block-6 run showed this on the native build, DR-12).

## Timing
- 21 Nov, desk work over existing runs: release-gate and full-box served runs (stack build against r2a), the block-6 runs (DR-12, DR-14), the tree-drafting run (DR-13), the verify-cost run (DR-16) and the stage-timing runs. Served layout: 4 XTX + 5 MI50 helpers, native pack.

## Verdict
- **On r2a an extra verify row costs about 3.2 ms, and most of it is expert work whose critical path is the CPU lane.** This is the one quantity behind every drafting result since 14 Nov, and it has never been measured by stage.
- **Block 6 is the best draft length at today's row cost and at any lower one**: each extra position keeps 0.75–0.99 tokens, above the break-even of c / (ms a token) ≈ 0.40.
- **Staged (21 Nov), not run:** a package in two parts. Part A (frozen, ~63 GPU min) times windows of 1, 2, 4 and 6 rows in one process each with the CPU lane and helper counts per window, plus a drafter-on arm to measure the draft pass on the stack. Part B (served on r2a, ~356 GPU min) re-runs DR-12's block 3 against selective block 6 with n ≥ 16 at four users and 8K cells. Part B's gates are DR-12's: one user faster (upper CI < 1.00) at 2K and 8K, two and four users no harm (lower CI > 0.98), identical bits. A third part (stage stamps inside windows) needs a new build and comes only after Part A.

## Notes / caveats
- The per-stage split is inferred from one-row stage data, served round times and the source; no stage data inside windows exists.
- The draft pass (2.24 ms a round) is from an older build; if it is larger on the stack, block 6 gains slightly more.
- The served CPU-lane share in windows is unmeasured; the package's served part logs it for the first time.
- The two studies differ on the row cost because they read different builds: 4.2–4.7 ms on the stack build and the native build (first study), ~3.2 ms on r2a (second study).

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
