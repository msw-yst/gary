# EB-09: castagna-veloce against mainline llama.cpp on four MI50s, same GGUF: decode is CPU-bound and about equal; castagna's prefill is 1.4–1.85× faster
Status: finding · Date: 2026-11-17
Code: none in this release (two external engines, run as built; the run scripts are private).

## What and why
- HX-33 timed one expert kernel at a time: castagna-veloce's fused Q2_K / Q3_K expert kernel was the fastest MI50 expert path we measured. This asks the end-to-end question: on our MI50s, does castagna-veloce's engine beat mainline llama.cpp on the same model file?
- Four MI50s alone (no XTX), both engines on the same DeepSeek V4.1 Flash GGUF (a ~2-bit build: IQ1_M / IQ2_XXS / IQ2_XS experts, 128.7 GiB, plus a 103 GiB Engram table on the CPU), the same flags and the same placement.

## Prediction
- Pre-registered: ten predictions, among them castagna-veloce at least 1.15× mainline's decode and an absolute decode of 25–55 tok/s. Four were FALSIFIED (decode was 4.6 tok/s), two HELD, four had NO DATA.

## Correctness
- Not compared: this is a speed comparison. The bench cells ran for both engines.

## Timing
- 17 Nov, the test machine's four MI50s. `llama-bench -ngl 999 -fa on -t 16 -b 2048 -ub 512 -p 512,2048 -n 128 -r 3 -sm layer`, with `-ot` putting the experts that do not fit on the CPU. Cell LA: the experts of 6 layers on the CPU; LB: 10 layers; LA2: LA again (drift). castagna-veloce `main` at 3483d4627 and llama.cpp b11870, both built for gfx906 (as HX-33).

- Decode across the cells: 3–4.6 tok/s for both engines (MEASURED).

## Verdict
- **On four MI50s this measures the CPU, not the MI50 kernels.** The model does not fit in 4 × 32 GB, so the experts of 6–10 layers run on the host, and that sets decode at 3–4.6 tok/s for both engines. The decode result says nothing about either engine's GPU kernels.
- **castagna-veloce's prefill is genuinely faster: 1.4× at 512 tokens, 1.85× at 2,048**, even with its own virtual-device split turned off (below).
- Its published 85.7 tok/s needs eight MI50s with the whole model in VRAM, a setup we did not test.

## Reproduce
- The `llama-bench` line above on any four MI50s, each engine built for gfx906, with an `-ot` rule that puts the experts that do not fit on the CPU.

## Notes / caveats
These favour neither engine on purpose, but readers should know them:
- **castagna-veloce needed a loader mapping to read this GGUF.** Its build at 3483d4627 does not read the file's tensor layout, so we added a name-and-layout mapping in its loader. No kernel or compute path was changed.
- **castagna-veloce's virtual devices were off** (`GGML_CUDA_VIRTUAL_PER_GPU=1`): by default it splits each card into three virtual devices, which our harness's device check refused. Its own code comment puts that split at about +20 % on pp2048, so its prefill lead here is, if anything, understated (INFERRED).
- The MI50s ran at the default `auto` power level, not `high` as castagna-veloce's README suggests.
- **castagna-veloce's server cells failed in our harness** (cause not diagnosed), so there are no first-token or drafting numbers for it. It may be our harness rather than the engine; not checked.
- One run of three repetitions a cell.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).

Sources: no published data extract for this card; the run summary is held privately.
