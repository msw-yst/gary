# SV-17: Build 17 = build 16 + the batched-path fusion + the cache fix that keeps promotion: 8 users +12.5 %
Status: kept (build 17, the release build of release 3) · Date: 2026-11-14
Code: in the fork's release commit (release 3). Build 17 = build 16 + `DS4_BT_FUSE=1` (FG-16 item 2) + `DS4_ECOWN=1` (HX-30), with `DS4_EC_FIX` unset (`DS4_ECOWN` refuses it). The two lines merged with no conflicts and no code of their own; every GPU kernel is identical to the build it came from (REPORTED from the build notes).

## What and why
- Both changes passed on their own the same day: the batched-path fusion +6.4 % with 8 served users (FG-16), the cache fix −12.5 % on the 8K first token (HX-30). They touch different stages, so they should add.
- Re-validation: identity first, then a served A/B against build 16 with alternating rounds.

## Prediction
- Against build 16: one user 2K decode +0.01 ms (−0.10 to +0.10), 8K decode −0.23 ms (−0.35 to −0.10), 8K first token −12.5 % (−15 to −9), 2K first token −4.3 % (−7 to −2), 32K +2.7 % (0 to +5); 4 users +5 % (+2 to +8) total, −5 % a token each; 8 users +7.5 % (+4 to +11) total, −7.5 % each. Pre-registered: yes, before the run.

## Correctness
- **check 0, both switches off:** identical to build 16 on short prompts with the drafter off and on, the batch test, the batched-fusion run's batch test, 32K, 110K and one served user (MEASURED).
- **check 1, both on, cache off:** identical on the same arms except 110K; the batched path engaged; two fresh 4-slot servers with 4 greedy requests at once gave build 16's tokens (MEASURED).
- **check 2, cache on:** 2.92 million picks, 0 counted twice (MEASURED). The batched path is reported, not gated, here: it engages only when 2 or more requests share a step, and check 2's steps are single.
- In the A/B, both audited probes of the new build: 0 picks counted twice (MEASURED).

## Timing
- 14 Nov, 4 × RX 7900 XTX + 4 × MI50 at 135 W. Served, sampled requests, drafter on; 4 slots for the one- and four-user cells, 8 slots for eight users. Rounds build 16, 17, 17, 16. A cold 31K-token probe read logged disk reads and page faults once a second.

## Verdict
- **Build 17 gives build 16's tokens and is faster for several users and for prompts up to 8K.** 7 of 9 predictions came in; the two misses are the 8-user cells, better than predicted.
- The 8-user gain is larger than the two changes measured apart (+6.4 % and +1.4 %) [I: they interact at 8 slots; not shown which way].
- **32K cold first token is 3 % slower.** Disk is ruled out (0 MB, 0 major faults in both). The read itself is only 55 ms slower; the 15 cache moves after it fit the settle-step suspect, which HX-31 then measured: it explains only about 0.13 s.

## Reproduce
- Both switches are in the release-3 commit: build 16's recommended environment with `DS4_EC_FIX` unset and `DS4_ECOWN=1 DS4_BT_FUSE=1`. The served benchmark client is not published; for single-process numbers, `tools/dsv41/bench-perms.sh` with those switches.

## Notes / caveats
- Build 16's 8-user rounds varied 177–184 tok/s; build 17's 202–203. The gain is still well outside that spread.
