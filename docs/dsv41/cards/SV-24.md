# SV-24: Native prompt reads through windows of 16 below 3,072 new tokens (`DS4_CHUNK_MIN`): 2K first token 18.5 → 8.9 s; four other native settings do not help
Status: superseded (adopted for native agent serving 17 Nov; the stack build's faster prompt path replaced it, SV-18) · Date: 2026-11-17
Code: in the fork's release commit (the switch is in build 17's source); run on the native build (internal build `nat18-r1`, commit d2a73071). Flags: `DS4_CHUNK_MIN=3072` (arm W). Also tested: `STRATA_DS4_HELPER_SLOTS=1700` (arms H, HW), a fresh expert profile (arm P), and a timing oracle that skips the CPU lane (arm L, output invalid).

## What and why
- Served on the native pack, a 2K prompt took about 20 s to its first token (SV-23). The engine reads a prompt in one of two ways: the chunked pass, which streams every expert the GPUs do not hold (12,688 experts, 59.6 GB a read on native) once per pass, or windows of 16 tokens, which touch only the experts each window picks (MEASURED from the flow lines; the two paths from the source). By default the chunked pass is taken from 512 new tokens (`DS4_CHUNK_MIN`'s default in the source; B0's reads of 128–511 tokens take 6.9 s, from 512 about 20 s). Agent turns mostly add 512–3,000 new tokens, so the windows should be cheaper there.
- The same run tried the other settings-only levers from the native serving plan: freeing MI50 room for the prompt helper, a fresh expert profile, and pricing the CPU lane.

## Prediction
- W: a read of 512–3,071 new tokens 3.5–23 s (against ~21–25 s); 2K first token × 0.45–0.75; decode × 0.97–1.03.
- H / HW: the prompt helper engages; reads of 512–8,192 tokens 6–14 s; 2K first token × 0.30–0.65.
- P: decode × 0.85–0.98. L: verify step × 0.65–0.90.
- 17 predictions in all. Pre-registered: yes.

## Correctness
- W, H, HW and P are settings, not new code; no identity test was run. L skips the CPU lane's experts and its output is invalid by design (a timing oracle).

## Timing
- 17 Nov, 02:34–04:01 UTC, 4 XTX + 4 MI50 at 135 W, native MXFP4 pack, served, 4 slots, drafter on; 2K first token over 6 requests; read times binned by new tokens from an agent-turn mix. Arms in order B0, H, HW, W, P, L, B1 (B1 repeats B0 for drift).

## Verdict
- **The window path halves native first token at agent read sizes: 2K 18.5 → 8.9 s, reads of 512–3,000 new tokens about 9 s instead of about 20.** Reads above about 3,200 new tokens get slightly slower, so the cut-off matters. Adopted for native agent serving on 17 Nov.
- **A fresh expert profile is not the lever** (decode 4 % worse). **The CPU lane is**: skipping it takes 8 ms off a verify step (44.5 → 36.4 ms) although it carries only 0.5 % of the picks. Moving those experts onto GPUs (mixed precision, QA-12) is the decode lever, not settings.
- The prompt helper's load check was fixed next; the helper then engaged but made native first token worse, because it still streamed the CPU-only experts (not carded here).
- **Superseded:** the stack build reads native prompts from the RAM store straight to the GPUs, 2K first token about 2.9 s with the chunked pass (SV-18). The release gate's servers set no `DS4_CHUNK_MIN`, so r2a was gated with the default 512 (MEASURED from their configurations). The cut-off was re-measured on the stack base; 256 was then adopted by an operator call against its run's "keep 512" (PF-17, PF-21).

## Reproduce
- Serve the native pack with build 17's environment plus `DS4_CHUNK_MIN=3072`; compare first-token times binned by new tokens.

## Notes / caveats
- One start per arm; six 2K reads per arm. The read-size bins hold 1–10 reads each.
- The engine's start-up line ("the chunked pass from 96 tokens") reports a different threshold (`DS4_PICK_MIN`), not `DS4_CHUNK_MIN`; the read times show the 3,072 setting took effect (MEASURED).
