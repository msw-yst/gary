# SV-27: From benchmark harness to service: a truthful `/health`, a `/ready` that waits for the GPUs to settle, restart on crash, stall counters; load to ready measured at 7.8 minutes
Status: done (server code and unit tests; not deployed; the GPU smoke test is staged, not run) · Date: 2026-11-22
Code: not in the release commit of Gary, our fork of Strata (internal branch only: server changes on top of r2a, carried into a second release candidate that adds the template fix of SV-28 and locks the RAM store's memory by default, HW-18). Flags: `STRATA_ENGINE_RESTART=lazy|eager|exit` (default `lazy`), `STRATA_READY_SETTLE_S` (10), `STRATA_READY_REQUIRE_EVICT` (1), `STRATA_STALL_MS` (400); server option `--release-manifest`.

## What and why
- Until 22 Nov the engine ran only inside test harnesses: a run started a server, used it for one package and stopped it. Nothing supervised or restarted it, and its `/health` answered 200 even while the engine was down. A desk study listed what it takes to run it as a service; this card covers the server changes that came out of it.
- The numbers that size the work come from the release gate (SV-25): how long a server takes to load, and what a crash costs the next user.

## Prediction
- Not a timed experiment. The study's estimates: eager restart spares the first user after a crash the ~470 s load; waiting for GPU memory evictions to settle before "ready" moves a mean 1.7 s (worst 8.8 s) off the first request's first token into load time (INFERRED from the release gate's first-cell evictions).

## Correctness
- 34 new CPU-only unit tests pass, including a fake engine that is killed with `kill -9` and brought back with no request; one existing test changed (a dead engine now gives 503). The full server suite: 529 tests, 1 failure that fails the same way on the unchanged base on the same host (a host issue) (MEASURED).
- **Nothing was tested on a GPU.** Two open risks: the GPU-eviction counters may not be readable inside the container, and the batch scheduler may not print its step lines at token time (INFERRED).

## Timing
- 21–22 Nov, desk and CPU only. Load time read from the release gate's run log (21 Nov, eight servers).

## Verdict
- **The server can now be supervised: it reports a dead engine, says when it is really ready, can restart at once, and counts stalls.** `/health` returning 503 while the engine is down is a contract change for any caller that treats non-200 as fatal; restarts stay opt-in (`lazy` by default).
- **A restart or rollback costs about 8 minutes of service on this machine**, almost all of it the 470 s load.
- Not done here: the service itself (unit, container image, front door, alerts) is drafted, not installed; the freeze root cause is open (SV-25's notes).

## Reproduce
- The server's unit suite, in the internal build named above (not published).

## Notes / caveats
- The 470 s load has not been split into disk read and GPU set-up, which decides whether a faster disk or a warm page cache would shorten restarts.
- The second release candidate has a gate package staged; it has not run.
