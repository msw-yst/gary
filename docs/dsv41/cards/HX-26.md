# HX-26: Expert prefetch (guess the next layer's experts and fetch them early): not viable; a cache leak found instead
Status: fixed in this release (the prompt-time expert-cache leak is confirmed, its cause found, and `DS4_EC_FIX=1` in build 16 removes it and the double count it caused, HX-28; prefetch not viable) · Date: 2026-11-13 (addendum 2026-11-14)
Code: the leak is in every build before 16 with the expert cache on (the default). The fix, `DS4_EC_FIX=1`, is in Gary's release commit (build 16; default off in the code, on in the recommended environment) and passed its leak test (addendum). `DS4_CACHE_HELPER_GUARD` is not in Gary's release commit. Flags: existing `DS4_AHEAD` (upstream's next-layer guess, off in serving); `--no-expert-cache` (existing; stops the leak, but is not the fix).

## What and why
- The idea: predict which routed experts layer L+1 (or the next token) will pick, and move or warm their weights before the router asks.
- This desk study read the served build's source and run logs to see where expert weights live today and what prediction could still buy. Nothing was run for the prefetch question.
- Its spin-off, a suspected leak in the expert cache during prompt reading, was then tested on the served build (13–14 Nov): three server lifetimes, each fed 50 distinct cold 2K prompts and then three 8K prompts: A with the expert cache on (the default), B with `--no-expert-cache`, and A2, a fresh cache-on server, as a drift control (10 prompts).

## Prediction
- Expert prefetch as asked: 0 ms a token on decode and 0 % on prefill (range −0.05 to +0.05 ms a token; the cost of the guess makes it negative). Pre-registered: yes, in the study note.
- Spin-off (the cache leak below): 0 % on a fresh server; after 50 chunked prompts, 2K time to first token +3 % (range 0 to +7 %), recovered by a fix. Pre-registered: yes, in the same note. The test had pass lines on the unheld count's slope and the first-token drift, and an abort line if B's decode came out more than 2 % slower than A's.

## Correctness
- Prefetch: not run.
- Leak test: not an identity run; decode speed was compared as an abort line only (B −0.47 % against A, MEASURED).

## Timing
- Desk study, 13 Nov, from the served build's source and existing run logs.
- Leak test: 14 Nov 00:56, build 15 served, 4 slots, one user at a time, after the hardware change (HW-09): 4 × RX 7900 XTX + 4 × MI50 at 135 W.

## Verdict
- **Not viable on this layout.** Every expert is already in GPU memory at decode; the one thing a guess could buy is already banked by the device-direct windows, at a 100 % hit rate. Do not build.
- **The leak is real, and bigger than predicted: LEAK CONFIRMED.** With the expert cache on, every prompt adds exactly 8 experts that stream from host memory on later prompts, and 2K time to first token rose 13.9 % over 50 prompts (predicted +3 %); without the cache there is no growth. A fresh process starts clean, and decode is unaffected. The cause, found in the source afterwards (addendum): the prompt path lets the cache swap a helper-held expert into XTX VRAM, evicting one that no helper holds (REPORTED).
- **A known issue of build 15, fixed in build 16.** Without the fix a long-running server's first token gets steadily slower (about +0.3 s per 50 prompts at 2K, and growing); restarting the server resets it. Turning the cache off (`--no-expert-cache`) stops the growth but loses the cache's benefit (8K first token 6.7 s against 6.1 s). The fix (`DS4_EC_FIX=1`, addendum) is in build 16 and its recommended environment.

## Reproduce
- Prefetch: not run. Leak test: no published run; the code is in the release commit, the benchmark client is not published.

## Notes / caveats
- The only configuration where expert prefetch matters is one XTX with experts in host RAM (the EB-03 layout), where upstream's `DS4_AHEAD` already exists.

## Addendum (2026-11-14): the cause, the fix (in build 16), and output that depends on uptime
- **Cause (REPORTED, from the source reading for the fix):** the chunked prompt path adds helper-held experts to the expert cache's hit list, which decode does not. The cache then promotes one hot helper-held expert per layer in the first 8 layers of every prompt into XTX VRAM and evicts a VRAM expert that no helper holds: exactly +8 host-streamed experts a prompt, per process.
- **The fix (`DS4_EC_FIX=1`, in build 16, this release; host code only; default off in the code, on in the recommended environment)** leaves helper-held experts out of the prompt path's hit list. Served, 4 slots, the same method as the leak test (50 cold 2K prompts, then 3 × 8K), arms A = fix off (the release behaviour), F = fix on, B = `--no-expert-cache`. Pre-registered: leak fixed (F's slope ≤ 0.5 a prompt, drift ≤ 1.5 %, F's answers the same before and after the 53 prompts); the 8K first token expected near B's level rather than A's; A's answers predicted to differ after the 53 prompts.
- **Leak fixed:** A +7.96 host-streamed experts a prompt and 2K first-token drift +15.8 %; F 0.000 a prompt and −0.9 %; 2K first token over all 50 prompts A 2.446 / F 2.290 s; decode F −0.9 % against A (MEASURED, cache-fix.txt).
- **8K first token at the no-cache level:** A 6.18 s, F 6.69 s, B 6.74 s. The cache's 8K benefit came from the same promotions that leak, so the fix gives it back (+8.1 % against the leaky cache) (MEASURED, cache-fix.txt). Run verdict: PARTIAL (leak fixed, 8K at B). Winning the 8K gain back without the leak needs a helper-side exchange (estimated 2–3 days [I]).
- **Answers that change with uptime:** the same 8 greedy prompts (content, reasoning, tool calls), asked of a fresh process and again after the 53 prompts: with the fix off, **6 of 8 differed**; with the fix on, 8 of 8 identical; the fix-off build on a fresh process gave the same answers as the build it was made on, 8 of 8 (MEASURED, cache-fix.txt). The differing answers stayed fluent and correct (for example "1001 = 7 × 11 × 13" both times) and parted at characters 14–97, which reads as near-tie flips, not damage (REPORTED from the run's answer files). Why the promotions change output is not proven: the helper and the XTX do not compute an expert bit for bit the same way, so moving one between them can flip a near-tie on its own [I]; a check of a second suspected path (an expert counted on both sides) was run afterwards and confirmed it: with device-direct windows, a promoted expert was also computed on its MI50 and summed twice (HX-28).
- These runs used a pre-16 build with the fix switched off as build 15's behaviour; build 15 runs the same cache code [I].

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
