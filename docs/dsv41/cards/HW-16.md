# HW-16: An MI50 HDP flush costs 1.3 µs; the stale-read rule holds on MI50 #5; the push all-reduce's MI50 fault test passes
Status: finding (closes three open items of HW-12 and the P2P write-up) · Date: 2026-11-18
Code: no engine change. Probes and the push all-reduce's fault-test tool on internal branches only. Flags: none. Runtime variable tested: `GPU_FORCE_BLIT_COPY_SIZE`.

## What and why
- [HW-12](HW-12.md) found that a peer reads stale data from MI50 memory that the MI50's own SDMA copy engine wrote, until the MI50's HDP is flushed. It listed four ways round it and left the cost of two of them (force blit copies; flush the HDP) unmeasured. The P2P write-up ([p2p-on-gfx906-and-gfx1100.md](../p2p-on-gfx906-and-gfx1100.md), section 7) also left open whether the push all-reduce's MI50 fault test, which failed 2 of 36 cells on a second machine because of a test bug, passes once fixed.
- Three short runs on the bench card, MI50 #5: (1) time every flush and fence mechanism and check which of them make SDMA-written data read exact for a peer; (2) repeat HW-12's decisive arms with MI50 #5 as the writer, a third owner card; (3) re-run the fault test with the fixed binary.

## Prediction
- (1) A host HDP flush costs a few µs and fixes the stale read. (2) The pattern repeats on the new card. (3) The 2 failed cells were the test's bug (fault delays converted with the wrong card's clock rate). Each was written as the run's prediction before it ran.

## Correctness
- (1), (2): every peer read checked word for word against a fresh pattern each repetition; pushes exact in every arm (MEASURED). (3): 0 wrong values (MEASURED).

## Timing
- 17–18 Nov overnight, the test machine, in gaps between other runs: MI50 #5 as the SDMA writer, a production MI50 as the peer reader (kernel reads, 32 / 64 KiB, 8 repetitions; 8 and 64 KiB for run 2). The fault test: XTX #4 as member 0 and MI50 #5 as member 1. Not a timing run for decode.

## Verdict
- **The flush is cheap:** 1.3 µs (2.5 µs p99 under SDMA load), under 3 % of a 64 KiB SDMA copy. Prediction held.
- **The fix must act on the owner:** an HDP flush of the owning MI50, or a system-scope release on its queue (a kernel's end, a release event). A host sync or a later SDMA copy does not help. A CPU reading through the BAR is never affected, so the problem is specific to the peer path.
- **Rule for gfx906:** keep peer-read MI50 buffers kernel-written (free). Where SDMA-written data must be pulled, flush with a write and read-back (1.3 µs) or a stream-ordered release event. A posted flush write alone also read exact here, but nothing guarantees it has landed before the read, so do not rely on it (INFERRED). Forcing blit copies works but costs 9–22 % of copy time.
- **The cause holds on a third owner card** (MI50 #5), with HW-12's pattern cell for cell.
- **The push all-reduce's protocol is closed on an MI50:** the 2 earlier failures were the test's bug. The engine itself converts delays per card.

## Reproduce
- The repro in [p2p-on-gfx906-and-gfx1100.md](../p2p-on-gfx906-and-gfx1100.md) section 3.5, adding between write and read: the host writing the owner's HDP flush register (its address is `HSA_AMD_AGENT_INFO_HDP_FLUSH`) and reading it back, timed.

## Notes / caveats
- MI50 #5 sat on a link limited to PCIe Gen1 x8 at the time, which is why its copies ran at about 1.8 GB/s; the SDMA / blit ratio, the flush times and the exact / stale pattern are what carry over (INFERRED).
- The fault test ran with 2 members (one XTX + one MI50), not 3 as on the second machine.
- Not done: MI50 #5 → XTX reads, kernel stores from MI50 #5, and the offset-rotation test of the P2P write-up's section 3.3.
