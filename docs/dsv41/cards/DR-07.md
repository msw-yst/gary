# DR-07: Sampled drafting inside batched decode, for concurrent users (`DS4_BATCH_DSPARK_SAMPLED`, `DS4_BATCH_DSPARK_MAX`)
Status: kept (build 13s; served) · Date: 2026-11-13
Code: in the fork's release commit. Flags: `DS4_BATCH_DSPARK_SAMPLED=1` (sampled drafting in batched steps), `DS4_BATCH_DSPARK_MAX=<n>` (at most n banks draft in a step; served at 3); server parallel slots (`PAR`) 4.

## What and why
- DR-04 put the drafter inside batched decode steps for greedy requests. Served traffic is sampled (temperature 0.6, top-p 0.95, top-k 20), so with several users at once the server took plain batched steps and lost the drafter.
- This change lets each bank draft and verify with the sampling rule inside one batched step, and caps how many banks draft in a step (`_MAX`), because a batch of verify windows grows fast.

## Prediction
- Through the server, sampled drafting with 2 users ≥ 1.10 × plain (REPORTED, from the 11 Nov run notes).
- With 3 concurrent users: +12 to +35 % total decode throughput over plain batched decode (REPORTED). Build 13s's confirmation line: drafted / plain ≥ 1.10 at 3 users. Pre-registered: yes, in the run scripts, before each run.

## Correctness
- Greedy rows in 9–16-row batch windows: batched = solo, 8 of 8 (REPORTED).
- Sampled rows can only be checked in distribution. The first distribution check failed at every position, including position 1: the random-number streams of different banks overlapped. That was a real bug; with it fixed, the check passed (REPORTED).
- Build 13s, measured: 600 sequences with sampled drafting at 3 users against 600 plain sequences, 10 tests at α 0.01 (Bonferroni): **PASS**; the control position's χ² p = 0.99 (MEASURED). Batched greedy = solo greedy, 8 of 8, with the prompt helper off; with it on, see SV-10.

## Timing
- 11 Nov: build 12 base, the server's batch path. 12 Nov: the concurrency build before the merge into 13s. 13 Nov 04:11: build 13s, pre-incident hardware (4 × RX 7900 XTX: XTX #1–3 Gen4 x16, XTX #4 Gen4 x8; 4 × MI50 at 135 W; XTX at minimum power cap with −50 mV; MI50 DPM `high`), PAR 4, the prompt helper off for this run.
- Throughput = total decode tok/s in the window when all users are active, 2K prompts, 512 new tokens each, 3 reps.

## Verdict
- **+22 % total decode throughput at 3 concurrent users, distribution-exact.** Kept; on in the served environment from build 13s (PAR 4, MAX 3).
- `_MAX` is a real trade: at 4 users MAX 3 is equivalent to plain, MAX 4 gives +11 %. Served at MAX 3, so 4 or more active users take plain batched steps.
- What limits several users now is the prompt, not decode: prompts are read one at a time (SV-11).

## Reproduce
- No published run: the code is in the release commit; a scripted public re-run has not been prepared for this card.

## Notes / caveats
- Seeded sampled outputs are not reproducible per seed on this server, even for an exact repeat; the distribution test compares distributions, never per-seed text (PF-11 addendum).
- The 1.44× at 2 users is on text that drafts well and is not a general figure.
