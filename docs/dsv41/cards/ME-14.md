# ME-14: How noisy a served A/B is: an A-against-A pilot sets the sample size, and a parser count is part of the gate
Status: method · Date: 2026-11-19
Code: no engine change. Run harness only.

## What and why
- Several served A/Bs on 18 Nov produced "gains" of 1–5 % that later runs did not reproduce, and one served pair had a within-arm spread of 21–29 % at n = 3 (CP-06). Before judging small changes, the same build was run against itself four times to measure the noise of each served metric.

## Prediction
- None as numbers; the output is the sample size needed per metric.

## Correctness
- The pilot's first verdict was INCOMPLETE: its 4-user cells found 5 prompt lines where it expected 4. The cause was the harness's parser, not the data: re-entry of a batched request writes an extra prompt line. The same family of bug made a drafter run count 8 of 6 requests (DR-12). Both were re-scored from the run logs with a fixed parser (MEASURED).

## Timing
- 18–19 Nov, the test machine: 4 × RX 7900 XTX + 4 × MI50; native MXFP4 pack, internal native build. Four A-against-A pairs, page cache dropped, the same warm-up, ABBA order.

## Verdict
- **Only four-user throughput clears a 1.5 % noise gate.** One-user decode and first-token changes of 2 % or less must be judged on bench or stage timers, plus a bounded served check that says "not worse", not on a served point estimate.
- **Size n before the run** from the pilot's s_d (the RA all-reduce run, AR-11, used n = 24 a cell this way), and make warm-up longer than 8 prompts.
- **A parser count is a gate too:** a harness that cannot count its own requests cannot be trusted to compare them; both INCOMPLETE verdicts here were the counter's fault, and the re-score is recorded as such.

## Reproduce
- Run the same build against itself, interleaved, and compute each metric's pair-difference spread.

## Notes / caveats
- Native build, one machine, one prompt set; s_d on the 2.25-bit pack was not measured this way.
