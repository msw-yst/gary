# HX-20: ddexp: the next single-stream bottleneck experiments (lane-wait fix, oracles, timestamps)
Status: finding (fix dropped; empty-all-reduce oracle explained 2026-11-11) · Date: 2026-11-10, updated 2026-11-11
Code: not in Gary's release commit (internal branch only) (experiment branch on top of build 11). Flags: `DS4_DD_NO_LANE_WAIT`, `DS4_DD_LANE_DELAY_US`, `DS4_INJECT_EMPTY`, `DS4_TSTAMP`, timing-only oracles (all default off).

## What and why
- These are pre-registered experiments to find what still sets the single-stream step after build 11. They ask five questions:
  - Does the lead wait for the CPU lane's empty answer each layer (H2)?
  - What does one extra dependent kernel cost, on the lead and on a member?
  - What would removing the helper wait, the MI50 maths or the all-reduce give? These are oracles that produce wrong outputs and are used for timing only.
  - Where does one token's time go per layer, from device timestamps on one clock?
  - Does the no-lane-wait fix help?
- Target slice: tp4h4 B1, ~14.4 ms a token in plain decode (15.2 ms a step in the batch test). Around 1,463 small dependent kernels run on the lead per token [I, desk model].

## Prediction
- Lane-delay slope ≈ 0.039 ms per µs if the lane wait binds, ≈ 0 below ~24 µs if not.
- No-lane-wait fix: tp4h4 B1 −0.5 to −1.2 ms if H2 holds.
- Empty kernel on the lead: 1.3–3.3 µs each.
- Oracles: no helper wait −0 to −0.3 ms; no MI50 maths ~0; empty all-reduce −0.5 to −1.0 ms.
- Pre-registered: yes. A design note with predictions and decision rules was committed before any run.
- Any identity DIFFER on a non-oracle flag stops the run.
- The fix is kept if it saves ≥ 0.5 ms at tp4h4 B1, is exact, and has no worse rep. It is dropped if it saves < 0.2 ms.

## Correctness
- Every non-oracle flag is IDENTICAL to the reference on decode, batch test and score, on tp4h4 and tp3h3 (MEASURED). That covers the lane delay, the no-lane-wait fix, the empty kernels and the timestamps.
- Every repeat of the fix arms is identical to the first (MEASURED).
- The oracle arms are timing-only by design.

## Timing
- Hardware: 4 × RX 7900 XTX (XTX #1–3 Gen4 x16, XTX #4 Gen4 x8) + 4 × MI50 32 GB at 135 W (Gen4 x4 each). XTX at minimum power cap with −50 mV. MI50 DPM `high` (CP-03).
- Software: ROCm 7.14 on Linux; Strata v0.2.9 plus Gary's changes. Kernel version: not captured in the published extracts.
- Plain decode is 256 tokens, drafter off, one run per arm, except where n is shown. The batch-test arms use 3 reps.
- The timestamps come from 63 recorded tokens × 40 layers. Clock fit rms is 16–26 ns on the XTX and 49–53 ns on the MI50. A refit from the raw alignment samples agrees within 0.3 µs.

## Verdict
- **The CPU lane is not binding.** Delays up to 50 µs change nothing, so H2 was wrong. The no-lane-wait fix saved 0.1 ms at B1 and was worse at B8. It was dropped, as the pre-registered rule required.
- **Kernel count is the largest single cost.** The lead's chain and attention pay about 2.7 µs per dependent kernel. A member's MoE has slack: 0.47 µs, because it isn't on the critical path. At ~1,463 kernels per token that is about 3.9 ms of a 14.4 ms token [I]. This prediction held.
- **The lead is the critical path at every MoE all-reduce.** It arrives last in all 40 layers, and the three members wait about 28 µs per layer, 1.0 ms per token. About 0.6 ms of that is the lead waiting on the helpers. Their ~75 µs window doesn't fit inside the ~66 µs of work the lead does after publishing, so they are about 20 µs late per layer. The other ~0.4 ms is lead-only work not yet identified [I].
- **All three oracle predictions were wrong.** Removing the helper wait or the MI50 maths saved ~0.7 ms each, against predictions of up to 0.3 ms and ~0. That is consistent with the join time above. An empty all-reduce made the token 0.47 ms *slower*, against a predicted saving of 0.5–1.0 ms. That is explained in the update below: the oracle changed the routing, not the timing model.
- **The measured slices don't yet add up to the step.** The MoE half is 5.86 ms, and the other ~8.5 ms (attention, hc, head, sampling, host) is not broken down. Picking the next change waits on that budget.

## Update 2026-11-11: the empty-all-reduce oracle explained
- **What the oracle skips** [I, from the code]: the decode all-reduce still puts each member's partial and still launches the sum kernel; the kernel only skips the flag waits and the peer reads, so each card keeps *its own partial* instead of the sum. Both launches a layer stay. The most it could save on the lead's path is the all-reduces' measured slice (0.29 ms, ANATOMY §2) less the launches' own time: **≤ ~0.24 ms**, not 0.5–1.0.
- **Why the token got slower** (MEASURED counts, `oracle-helper-counts.txt`): with every card's hidden state wrong after the first all-reduce, the lead routes from wrong values, the tokens degenerate, and the experts picked are no longer the hot set held in XTX VRAM. Helper experts a token went from 44.2 to 130.3 (2.95×), and the share of helper waits the lead could skip fell from 74.9 % to 41.3 %: about 53 more helper waits a token.
- **Arithmetic** [I]: 53 more waits at the reference's ~16 µs a wait gives +0.5 to +0.85 ms (the cost is the slowest helper a layer, not a sum). Net of the all-reduce saving (−0.05 to −0.24 ms), that is +0.3 to +0.8 ms, which brackets the measured +0.47.
- **So the oracle does not contradict the budget.** It measured a run with three times the helper traffic. The two oracles that saved time were perturbed the same way, less: 50.3 and 70.0 helper experts a token against 44.2. Their deltas are slightly confounded, though their helper waits are removed anyway.
- **Lesson for oracles on this engine:** an oracle that corrupts values also changes routing, and routing decides which hardware does the expert work. Timing-only oracles need a check that the helper and VRAM expert counts match the reference before their delta is read. A discriminator run that keeps the routing fixed was written and has not run.

## Notes / caveats
- These are single runs per arm in plain decode. Run-to-run spread on the reference was 0.016 ms.
- All timings are at short context (256 decoded tokens after a short prompt). Real agent traffic runs at 50–115K tokens of context ([SV-08](SV-08.md)), where attention costs more. A context sweep is planned.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
