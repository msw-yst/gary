# NX-19: Expert arenas on 2 MiB hugetlb pages (KFD userptr eviction)
Status: kept (pool: arena on hugetlbfs with 35,000 pages reserved; opt-in by path) · Date: 2026-11-22
Code: the hugetlbfs shared arena is on the development branch, not yet in this tree ([Settings](../README.md#settings)); private arenas need no code change (the engine already tries `MAP_HUGETLB` first). Flags: `shared-expert-arena=<file on a hugetlbfs mount>` (`STRATA_SET`); host: `vm.nr_hugepages`, a hugetlbfs mount with `pagesize=2M`.

## What and why
- The first pool trial ([NX-14](NX-14.md)), and one later run with two private-arena servers, stalled at a first request: the engine waited on GPU work that never started. Two private 68 GB arenas left 59-61 GiB of host RAM available; nothing stalled at 114 GiB or more.
- The mechanism: an arena registered with the GPU (`hipHostRegister`) on 4 KB pages is a KFD userptr range. When the kernel moves one page of it (reclaim, swap-out, compaction), KFD stops every queue of the process on every GPU until the range is faulted back in, and under memory pressure that restore can keep restarting. The kernel log shows nothing; `/sys/class/kfd/kfd/proc/<pid>/stats_<gpu>/evicted_ms` counts it. Hugetlb pages are never reclaimed, swapped or compacted.
- The arena of our Q4_K file is 34,802 2 MiB pages (67.97 GiB); the pool's shared file 34,803 with its header.

## Prediction
- Pre-registered: yes. Private arenas: post-load eviction <= 100 ms, load-time eviction <= 10 % of the unfixed arm, same speed, exact. Pool: per agent >= 0.97x the /dev/shm arena at 4+4 and 8+8, eviction no worse, >= 80 GiB available, identical texts.
- Estimate: eviction ~0 on hugetlbfs, same speed (ESTIMATE).

## Correctness
- Reference text on both servers / workers in every arm; batched == solo, loaded == alone and worker 1 == worker 2 8/8 in the pool arms; every speed-prompt text identical across /dev/shm and hugetlbfs cells (MEASURED, short-prompt checks).

## Timing
- Hardware: 2 × RX 7900 XTX 24 GB (272 W cap), 4 × Instinct MI50 16 GB (135 W cap), EPYC 7642 (48 cores), 256 GB DDR4-2666 (251.5 GiB visible).
- Workload: private-arena servers MTP on, 4 slots, 1 to 4+4 users; pool 8 slots, MTP off, 4+4 and 8+8; 384 tokens, temperature 0. Pool arms alternated (H S H S at 35,000 pages); `evicted_ms` read per process at load and at the end of every cell.

## Verdict
- Private arenas: the arena's eviction is gone (85-98 % of the load-time eviction removed, none after load, no stall in 8 server loads, same speed, exact). Partial: a smaller load-time eviction from another registered 4 KB range remains, not identified.
- Pool: adopted on hugetlbfs with a reservation sized for one arena (`vm.nr_hugepages=35000`): every bar met. Not adopted at 70,000 (0.968x, more eviction).
- Neither run settles whether the earlier stalls were this mechanism (no stall happened in the unfixed arm either: 2 stalls in 17 such cells overall); `evicted_ms` is the direct measurement.

## Reproduce
- Host: `vm.nr_hugepages=35000` (persist it in `/etc/sysctl.d`; on a running host drop caches and compact memory first, then read back `HugePages_Total`), and a hugetlbfs mount with `pagesize=2M,size=70000M`.
- "Layout 3" in [README.md](../README.md#launch) with the mount in the pod and `shared-expert-arena=` naming a file on it. Each worker logs "MAP_SHARED hugetlbfs file ... pages"; the second skips the read.

## Notes / caveats
- While 70,000 pages are reserved, a /dev/shm pool at 8 slots does not fit in the remaining RAM, and the shared-arena path skips the RAM pre-check, so it would end in reclaim or OOM rather than a refusal.
- Private-arena servers need their own reservation (2 x 34,802 pages); their arenas fall back to 4 KB pages, and the bug, without it.
- The engine's arena RAM pre-check compares the arena with MemAvailable, which leaves out free huge pages; a second private server under a reservation waits 20 s and warns that it is short. Not fixed.
- Absolute numbers come from a private prompt set (8 prompts, not published); ratios between arms of the same run are the comparable quantity.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output), ESTIMATE (our arithmetic) or INFERRED (our own reading).
