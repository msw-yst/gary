# HX-31: Settle the cache after the first token (`DS4_SETTLE_AFTER`): little gain, and a risk for short answers
Status: parked · Date: 2026-11-15
Code: not in the published release; the code is not in the public commit. `DS4_SETTLE_AFTER`, default off: `=1` runs a prompt's cache settle right after its first token (blocking); `=2` spreads its rounds over the decode ticks.

## What and why
- After a prompt is read, the expert cache spends up to 800 ms moving hot experts into VRAM (its settle step). That time counts in first-token time. With build 17's cache fix it has more moves to make, which fit build 17's 3 % slower 32K first token (SV-17).
- This change moves the settle after the first token, so the user sees the first token sooner.

## Prediction
- Against build 17: 32K first token −0.45 s (−0.60 to −0.30); 2K −2 %, 8K −1 %; decode and several users unchanged (±0.10 ms, ±2 %). Pre-registered: yes, before the run.

## Correctness
- **check 0, switch unset:** identical to build 17 on short prompts, the batch test and 32K, and a probe's tokens and prompt timings identical (MEASURED).
- **check 1:** with `=1` and with `=2`, the same three end placements (by hash) as without it, and `=1` gives the same greedy tokens (MEASURED). So the change moves when the settle runs, not what it does.
- In the A/B, both audited probes: 0 picks counted twice (MEASURED).

## Timing
- 15 Nov, same machine and client as SV-17. Served A/B, rounds build 17, `=2`, `=2`, build 17.

**Follow-up (same day, from the engine logs of this run and SV-17's):** all of the 8K decode gain comes from **one** of the six 8K requests, which took a different sampled token path. Drafts kept on that request: build 16 73 of 155, build 17 115 of 218, this build 161 of 225 (3.45 / 2.92 / 2.18 s). The other five requests are −0.8 %. Time per decode step is not faster (that request 20.7 → 23.0 ms a step). Each build repeats its own path exactly, which is why the spread between rounds is near zero (MEASURED from the logs; the reading is ours [I]).

## Verdict
- **Parked.** The settle step is only about 0.13 s of the 32K cost, not the 0.45 s predicted. About 0.4 s against build 16 is still not explained.
- The 8K decode "gain" is a token-path effect, not a speed-up.
- Risk found in review: after a short answer (1–32 tokens), a leftover settle runs blocking and cannot be interrupted, so the next request can wait up to about 1.6 s. Agent tool-call traffic looks exactly like that [I]. It needs to be interruptible, then an A/B with short-answer traffic, before it goes anywhere.
- The 32K gap: on a fresh server the read itself is the same in all builds (17.8–17.9 s, 0 disk). It only appears after about 33 earlier requests (build 16 18.19 s, build 17 18.63 s, this build 18.50 s) (MEASURED). It sits in the read; cause not shown.
