# HX-23: Rewritten MI50 expert kernels (more waves, fewer registers): exact, but 0.33 ms slower
Status: dropped (slower; cause inferred from the code objects) · Date: 2026-11-11
Code: in the fork's release commit. Flags: `DS4_MK_GU=1`, `DS4_MK_DN=1` (default off; knobs `DS4_MK_PH`, `DS4_MK_AO`, `DS4_MK_GU_TPB`, `DS4_MK_DN_TPB`).

## What and why
- The windows the lead waits for are one-expert (~75 µs) or two-expert (~106 µs) MI50 windows, and about two thirds of each is expert maths (HX-22). The earlier finding that MI50 kernels are a small share (HX-15) predates the device-direct windows and skipping, so it no longer held for the windows on the critical path.
- A desk analysis of the gfx906 kernels (compiler resource reports and the generated code) found them bound by vector-instruction issue, not by HBM2 bandwidth: the VALU floor is 1.6–1.8× the bandwidth floor, and the kernels run at about half of the VALU floor. The gate/up kernel uses 107–115 VGPRs, so at most 2 waves a SIMD, and at one live expert only about 1.6 waves a SIMD across the card [I].
- The rewrite keeps every lane's arithmetic and changes only the work split:
  - `DS4_MK_GU`: gate rows and up rows on different half-waves, the up sum passed through LDS, SwiGLU on the gate half: 81–84 VGPRs, so 3 waves a SIMD, and six times as many waves at one expert;
  - `DS4_MK_DN`: the down kernel's activations loaded per step instead of hoisted for the block: 76–84 VGPRs, 3 waves.
- These kernels engage only for one-row windows (B1, drafter off). Verify windows (2–4 rows) and batches take other kernels.

## Prediction
- Gate/up at one expert 27.5 → 17–23 µs; down 17–18.6 → 13–15.5 µs; one-expert window 75 → 60–68.5 µs [all ESTIMATE from the instruction counts].
- B1 ms a token: −0.15 to −0.31 alone; **−0.05 to −0.15 on top of the helper-window levers** (the wait is mostly gone by then). B8: 0 ± noise.
- Disproved if the B1 gain is smaller than −0.08 ms alone, or if a kernel bench shows the new gate/up at ≥ 0.9× the old time.
- Pre-registered: yes, in the kernel A/B script and the build-12 run script, both committed before the run.

## Correctness
- Bit-identical by construction: each output row's 32 lanes run the same sub-blocks in the same order with the same fused multiply-add chain and the same cross-lane reduction tree; only which half-wave runs the gate or the up chain changes.
- End to end, the stack with these flags is IDENTICAL to off on plain decode, drafter decode (greedy) and batch-test B 1/2/8, and the engine's new-kernel counter is non-zero in every MK run, so the kernels engaged (MEASURED). That counter (632) counts calls while the window graphs are captured, not launches a token: a window launches one gate/up and one down kernel in both arms [I].
- The kernel-level memcmp against the portable kernels (every type pair, 1 and 2 experts) was written but not run.
- A side effect, fixed: the first build of these kernels also emitted empty copies into the XTX code object, which moved the XTX expert placement and broke byte identity with build 11 (QA-08).

## Timing
- Hardware: 4 × RX 7900 XTX (XTX #1–3 Gen4 x16, XTX #4 Gen4 x8) + 4 × MI50 32 GB at 135 W (Gen4 x4 each). XTX at minimum power cap with −50 mV. MI50 DPM `high` (CP-03).
- Software: ROCm 7.14 on Linux; Strata v0.2.9 plus this fork's changes (the build-12 binary, SV-09).
- B1 plain decode, 64-token prompt, 256 tokens, drafter off, 3 interleaved reps, as the last step of the build-12 stack.

## Verdict
- **Slower, not faster: +0.33 ms a token at B1, against −0.05 to −0.15 predicted.** The prediction is disproved. The ranges do not overlap, so this is not noise.
- The output is exact, so this is purely a timing result. MK is off in build 12.
- **Cause: occupancy rose as designed, but occupancy was not what limited the old kernels** (INFERRED from the gfx906 code objects of the binary that ran, and an occupancy analysis of the launch shapes; not timed). Details below.
- **Keep MK off.** An exact re-tile of these kernels tops out at about −0.1 ms a token, realistically 0 to −0.05, which is inside the B1 rep spread. One variant reachable with the existing knobs (batched lookups, two tiles a block, gate/up only) remains; it is gated on a single-card kernel micro-bench and has not run.
- Sending verify windows to the gfx906 kernels (`DS4_G906_NEMAX=4`, a separate existing switch) did not help production either (+0.6 %, within the spread), and stays off.

## Cause (INFERRED from the gfx906 ISA and an occupancy analysis; not timed)
- **The occupancy claim held.** In the code object of the binary that ran, the new kernels use 76–84 VGPRs (IQ2_S gate/up 105), no spills, no scratch, so 3 waves a SIMD (2 for IQ2_S), as designed.
- **But the old kernels were capped by their grid, not by registers.** At one expert, the old gate/up grid supplies only ~1.6 waves a SIMD across the card, below its 2-wave register cap. Freeing registers could not raise occupancy on the same work; only the re-tile did that.
- **The register cut was bought with instruction-level parallelism.** In the default variant (`DS4_MK_PH=2`), the compiler serialised the codebook lookups: each LDS read waits for the one before it. Global loads in flight fell from 16–24 to 4–8, and the activations are re-read at every step instead of held in registers. Each wave now waits on a memory round trip and four LDS round trips per sub-block, in series, and three waves do not cover that. The same kernels at `DS4_MK_PH=1` keep their lookups batched at 82–87 VGPRs.
- **The re-tile made the grid 6× bigger with no less work on the busiest SIMD.** Gate/up at one expert: 576 blocks (3,456 with the empty groups) against 96 (576). The busiest SIMD issues about 6,060 vector instructions against 6,102 before (−0.7 %): the better balance is spent on a per-wave prologue (scalar table loads, the codebook copy, barriers) that now runs five times as often. Counting that, vector instructions per 32 weights rose from ~102 to ~121. The empty-group blocks, which used to drain through slots the live blocks left free, now queue behind them in a full machine.
- **Estimated cost: +8 to +12 µs a helper-pick window** on the lead's critical path, i.e. +0.33 ms over the ~27–39 layers a token with a pick. That is consistent with the measured +0.33 ms [I]. The helper counters (experts a token, joins, skipped waits) are identical in both arms, so the routing did not change (MEASURED).
- An earlier bench by the kernels' original author had already pointed this way: forcing the old kernel to 3–5 waves a SIMD made it slower, and a denser grid was slower too.

## Lesson
- The plan's first GPU step was a single-card kernel micro-bench (old against new kernels on one MI50, byte-compared and timed). It was skipped, because its build was held behind other work, and the kernels' first contact with a GPU was the engine timing run. The micro-bench would have shown the regression in minutes, on one card, before any engine time was spent.
- Kernel changes now run their micro-bench first, and go to engine timing only if it clears a pre-set bar.

- No published run: the code is in the release commit; a scripted public re-run has not been prepared for this card.

- The +0.33 ms is the stack step only; MK was not run alone against build 11.
