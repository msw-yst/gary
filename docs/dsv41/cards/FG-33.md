# FG-33: On native decode the BF16 matvec (−1.26 ms) and split-KV attention (−1.13 ms) stack fully, −2.37 ms a token (11 %); a bigger CPU-lane prefetch is slower
Status: finding (`DS4_BF16MV` on in release candidate r2a; `DS4_ATTN_SPLIT` held for quality; `DS4_MX_PF` and `DS4_LP_ROUTE` dropped) · Date: 2026-11-21
Code: the three switches are in the fork's release commit, default off (`DS4_BF16MV` since release 4, FG-20; `DS4_ATTN_SPLIT`, `DS4_MX_PF` and `DS4_LP_ROUTE` from upstream or earlier builds). Measured on internal builds `groupa-r1` (commit bea52585) and `groupa2-r1` (8030c73e), which add per-window switching and join / lane stamps. Flags: `DS4_BF16MV=r2u4n`; `DS4_ATTN_SPLIT=1` (split-KV decode attention); `DS4_MX_PF=512|1024` (CPU-lane MXFP4 kernel prefetch distance, bytes); `DS4_LP_ROUTE=1` (routing top-k per warp); `DS4_AF_SCHED` bits 512 / 1024 / 2048 / 4096 / 8192 switch them per window.

## What and why
- A re-evaluation of earlier write-offs found that `DS4_BF16MV` (FG-20) had been lost in a merge and never reached the stack build, and that split-KV decode attention had never been tried on the XTX (its code note says no gain on another GPU). Both act on decode attention, which is BF16 on the native pack.
- The same runs asked who is last into the lead's join (stamps inside the join kernel), and whether a bigger prefetch speeds up the CPU lane's expert kernel.

## Prediction
- `DS4_BF16MV` on native decode: no effect or ≤ 0.3 ms a token (recorded before the run).
- Additivity of BF16MV and ATTN_SPLIT: pre-registered as a test (excess within noise); no band for MX_PF.

## Correctness
- BF16MV: identical to all-off on 4,000 ids and 1,280 windows (EXACT PASS) (MEASURED).
- ATTN_SPLIT is not bit-exact by design (a different summation order). A separate teacher-forced quality test (12 prompts, 2,900 positions, windows of 1–4 rows, against hosted references) found KL change −0.00024 [−0.00050, +0.00003] and top-1 change +0.07 pp [−0.62, +0.76] (30 positions lost, 32 gained): **UNRESOLVED**, because the top-1 bound misses its −0.3 pp bar (MEASURED).
- MX_PF and LP_ROUTE: identical to all-off (MEASURED).

## Timing
- 21 Nov, the test machine, 4 XTX + 5 MI50 helpers, the native MXFP4 pack, frozen placement, greedy, drafter off, 1 user 2K, 4,000 tokens, untraced. In-process ABBA: first run 60 blocks an arm pair; second run 14 blocks a mode (off / ATTN_SPLIT / BF16MV / both) and 20 blocks for MX_PF. A freeze guard drops tokens over 400 ms or 10× the median.

## Verdict
- **Two real wins among written-off or lost items, and they stack fully: −2.37 ms a token, about 11 % of one-user native decode.** BF16MV beat its prediction (−0.94 to −1.26 against ≤ 0.3) and is exact; it is on by default in release candidate r2a. ATTN_SPLIT (−1.06 to −1.13) is held. Decision (21 Nov): ship r2a first and hold the split until a quality pass that covers the drafter's verify windows passes, because the split also changes those windows. That pass (windows of 1–4 rows) came back UNRESOLVED, so the split did not ship.
- **The lead's join wait is the CPU lane, and the lane is busy computing**, not dispatching or signalling: 2.8 ms a token, nearly three times the earlier timer figure. The levers are fewer experts on the CPU per token (placement) or a faster CPU expert kernel.
- **MX_PF is explained as a write-off:** a bigger prefetch slows the CPU expert compute itself (cache or bandwidth contention). LP_ROUTE is off the critical path. Both stay off.

## Reproduce
- The switches are in the release; the per-window A/B and the stamps are on internal builds only.

## Notes / caveats
- **Caveat found later (22 Nov):** the standard greedy 2K bench text falls into a 23-token loop at token 549 (126 distinct ids in 4,000). Speed deltas of the attention switches should not depend on which experts are picked, but the CPU-lane shares (who is last, the lane's 2.8 ms) measure that loop's experts and may not hold on real traffic (INFERRED).
- The two runs' BF16MV figures differ (−0.94 / −1.26); both are far outside noise.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
