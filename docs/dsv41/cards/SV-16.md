# SV-16: Build 16, the release build: five changes on build 15 and four upstream fixes
Status: kept (build 16 is the release build; identity PASS against build 15; served speed measured, then a same-day A/B) · Date: 2026-11-14
Code: in Gary's release commit. Build 16 = build 15 + `DS4_XK_QA` and `DS4_ATTN_MERGE=3` (FG-16), `DS4_IXS_DISPATCH` (FG-12), `DS4_PF_HELPER_MAXP` (PF-13), `DS4_EC_FIX` (HX-26, HX-28), and four upstream correctness fixes (SV-14 addendum). Every new switch is off by default in the code. Recommended environment: build 15's served one with `DS4_ATTN_MERGE=3` (instead of `=2`) plus `DS4_XK_QA=1 DS4_IXS_DISPATCH=16384 DS4_PF_HELPER_MAXP=8192 DS4_EC_FIX=1`.

## What and why
- Build 16 merges what passed on 13–14 Nov: two exact decode fusions, the indexer dispatch, the prompt helper's length cap, and the expert-cache fix, which turned out to fix a correctness bug as well (HX-28). With them come four upstream correctness fixes. The two lines (fusions and fix; upstream fixes) merged without conflicts.
- Re-validation: identity against build 15 first, then the final served benchmark's matrix (SV-14's client, 4 and 8 slots) against build 15's run of the night before.

## Prediction
- Identity: every comparison IDENTICAL.
- Served: one user −0.40 ms a token (−0.50 to −0.30); 32K cold first token 18.4 s (18.0–19.0); 8K first token +8 % (+3 to +14 %: the fix gives up the leaky cache's gain); 2K first token ±10 %; 4, 6 and 8 users ±3 %. Pre-registered: yes, before the run.

## Correctness
- Machine code: against the fusion-and-fix line's build, every kernel identical except the 6 routing kernels the upstream router guard changes (on both architectures), each identical to the upstream-fix build's (REPORTED from the build notes).
- **Identity: PASS.** 8 single-process comparisons, stdout IDENTICAL with the same expert placement: new switches unset (decode, drafter decode, batch test) and as recommended (the same three, plus a 32K and a 110K prompt against build 15 with the prompt helper off, since the cap reads prompts that long without it); one served user, greedy, 1,025 token lines: IDENTICAL (MEASURED).
- These comparisons moved no expert through the cache, so they do not reach HX-28's path; build 16 closes that path with `DS4_EC_FIX=1` (HX-28).

## Verdict
- **Build 16 gives build 15's tokens and is the build in this release.** With `DS4_EC_FIX=1` it also closes the double count build 15 had when served (HX-28).
- **Long prompts:** cold 32K first token 23.1 → 18.3 s, as predicted (the cap, PF-13).
- **8K prompts:** first token +14.4 % (5.9 → 6.7 s), just outside the predicted +3 to +14 %. This is the fix giving up the leaky cache's 8K gain (HX-26 measured 6.7 s as well): the price of correct output.
- **Several users:** within ±3 % at 4, 6 and 8 users, as predicted. At 4 slots, 2 and 3 users read −5.1 % and −2.8 % (not pre-registered).
- **One user, served decode: slower, and the cause is known (update, same day).** This run could not separate it (+0.32 ms at 4 slots, −0.19 ms at 8 slots, against build 15's run of the night before; prediction score 3 of 5 in). Two later runs answered it. In one process, build 16's five changes are worth −0.44 ms a token (ablation, row above). Served, a same-day A/B with alternating rounds shows one user **5.3 % (2K) and 8.7 % (8K) slower** per token, while 32K first token is 18.3 % faster and 4 and 8 users are 2–4 % faster. A further A/B on build 16 with only `DS4_EC_FIX` switched off gave one user −4.6 % (2K) and −8.4 % (8K) a token and −12.4 % on the 8K first token: the fix stops the expert cache moving hot experts into XTX memory after a prompt, and that move is what made build 15 faster for one user (MEASURED). The fix stays: without it batched output is wrong (HX-28). A fix that keeps the move and still counts each pick once is measured but not in this release: [UPDATE-2026-11-14.md](../UPDATE-2026-11-14.md).
