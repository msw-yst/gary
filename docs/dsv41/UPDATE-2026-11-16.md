Build 17 is now the release build. Its recommended environment is build 16's with `DS4_EC_FIX` **unset** and
`DS4_ECOWN=1 DS4_BT_FUSE=1` added (`DS4_ECOWN` refuses to load together with `DS4_EC_FIX=1`). Both new switches are
off by default in the code. `docs/examples/dsv41-serve.sh` and `tools/dsv41/bench-perms.sh` still set build 16's
environment, so that the published grid stays reproducible; change the two switches there to run build 17.

Not in release 3: build 18's swap (`DS4_ECSWAP`, [HX-32](cards/HX-32.md)), `DS4_SETTLE_AFTER` ([HX-31](cards/HX-31.md)),
`DS4_HSTEP_HEAD`, and the measurement-only builds (phase timer, Engram trace, expert histogram, expert-input capture).

## Did the gfx906 expert kernels change? No.

- **Source.** Between release 2 (build 16) and build 17, the files that hold the gfx906 expert kernels
  (`ds4_iq.cu`, `ds4_iq.cuh`, `ds4_iq_g906.inc`, `ds4_tq.cu` and their CPU references) are unchanged. Build 17 changes
  seven files; the gfx906-relevant lines are the cache-fix bookkeeping in the helper's planning and join kernels, not
  the expert matrix-vector kernels.
- **Machine code.** Every function in build 17's gfx906 code objects was compared with build 16's after
  disassembly: 1,341 identical, 11 changed, 1 new. The changed ones are `DS4_ECOWN`'s routing, helper-head and join
  kernels (`route_publish*`, `route_pair_kernel`, `helper_dd_head_kernel` ×4, `dd_join_k`, `dd_join_comb_kernel`); the
  new one is its check kernel. No expert matrix-vector kernel changed (REPORTED from the build's machine-code check).
- **The QBENCH binaries** were built from a measurement branch on top of build 17. That branch adds the bench's
  `--pool-file` mode and two measurement-only switches elsewhere in the engine; the expert-kernel sources it compiles
  are build 17's, byte for byte. So the MI50 and XTX timings below are the kernels in this release.

## MI50 (gfx906): our expert kernels against llama.cpp and castagna-veloce

One routed DeepSeek V4.1 Flash expert (5120 × 2304, gate + up + down), real expert bytes, 40 experts rotated so the
reads are cold, on one MI50. GPU µs is the kernel time per expert from a rocprofv3 kernel trace; batch B is how many
rows picked that expert; ours at B 1 is the engine's one-token path, at B 2–8 the helper's window path. Full table
(B 1, 2, 4, 8, GPU and wall time), method and caveats: [HX-33](cards/HX-33.md).

| Format | B | ours GPU µs | castagna-veloce | llama.cpp b11870 | fastest |
|---|---|---|---|---|---|
| IQ2_XXS | 1 | **51.6** | 70.2 | 79.6 | ours |
| IQ2_XXS | 8 | **170.5** | 210.7 | 228.4 | ours |
| IQ2_XS | 1 | **53.1** | 62.3 | 81.1 | ours |
| IQ2_XS | 8 | **174.4** | 228.8 | 243.9 | ours |
| IQ2_S | 1 | **56.2** | 134.1 | 91.0 | ours |
| IQ2_S | 8 | **175.3** | 317.8 | 257.0 | ours |
| MXFP4 | 1 | 80.8 | **54.2** | 58.5 | castagna |
| MXFP4 | 8 | **244.9** | 299.8 | 288.4 | ours |

- **2-bit (IQ2) experts: ours is the fastest of the three at every batch size measured (1, 2, 4, 8).**
- **MXFP4 at batch 1–2: ours is about 1.5× slower** than both references (80.8 against 54–59 µs). At batch 4 the three
  are level; at 8 ours is ahead. A faster MXFP4 kernel for gfx906 clearly exists.
- **castagna-veloce's fused Q2_K/Q3_K expert kernel is the fastest expert path measured on the MI50:** 29.1 µs per
  expert (12.8 MB of weights, about 440 GB/s, 43 % of the MI50's 1024 GB/s), 9.6 µs at a 768-row slice and 6.5 µs at
  512. With its fusion off, 48.5 µs; llama.cpp on the same layer 52.5 µs. It is for Q2_K/Q3_K, a different quantisation
  from the IQ2 packs this engine serves, so it is a yardstick, not a drop-in.
- **Accuracy.** Our output was checked against a CPU fp32 reference in every cell: rel_max 1.0–1.3 %, rel_rms
  1.1–1.2 % (the int8 rounding of the activations, alike for every format), no non-finite values, no launch errors.
  castagna-veloce and llama.cpp were only checked for non-finite values (none); their error was not measured.

## The MI50 helper's round trip

A helper request with one expert takes **104.6 µs** (p50) from the lead's side, of which the expert kernels are about
63 µs. Copying in, copying out and waiting make up the rest. Replaying the request as a graph, with kernel-side input
fetch, zero-copy output and a flag wait, brings it to **68.9 µs (−34 %)**, with output bitwise identical. A second
expert in the same request adds about 60 µs. [HX-34](cards/HX-34.md).

## RX 7900 XTX (gfx1100)

On the XTX the picture is the other way round: at batch 1 our IQ2 expert path is **1.45–1.48× slower** than llama.cpp's
(47–53 against 32–36 µs GPU), from slower expert kernels (37.6 against 29.7 µs) and three small extra launches; at
batch 4–8 ours is faster (0.51–0.83×). Our MXFP4 is 1.4–2.3× slower at every batch. A tensor-parallel 1/4 slice of an
expert still takes 52–75 % of the whole expert's time. castagna-veloce did not compile for gfx1100. [FG-19](cards/FG-19.md).

## Validation: does our engine compute what upstream Strata and llama.cpp compute?

**Yes.** Teacher-forced on llama.cpp's greedy continuations of 12 real agent prompts (2,658 positions, 2K–50K-token
contexts), same IQ2_XS 2.25 bpw weights, all three engines on 1 XTX with the routed experts in host RAM:

| engine | KL from llama.cpp (nats a token) | top-1 agreement |
|---|---|---|
| upstream Strata v0.2.9 | 0.00414 | 96.99 % |
| this fork, build 17 | 0.00417 | 96.50 % |
| difference (ours − upstream) | +0.00003 (pre-registered floor 0.002) | −0.49 points (floor 0.5) |

Pre-registered verdict: **ENGINE PASS.** Free-running greedy text first diverges after a median of 18–21 tokens, from
near-ties rounding differently on the GPU, not from errors. [QA-10](cards/QA-10.md).

## Validation: how far is the 2.25-bit model from the hosted model?

Against a hosted API's own greedy continuations and top-20 logprobs on the same 12 prompts (2,900 positions; cost
EUR 0.07):

| arm | KL from hosted (nats a token) | top-1 agreement |
|---|---|---|
| 2.25 bpw IQ2_XS, upstream Strata | 0.0438 | 90.34 % |
| 2.25 bpw IQ2_XS, this fork | 0.0434 | 90.28 % |
| native MXFP4 experts (unquantised), this fork | 0.0054 | 96.03 % |
| hosted against itself, re-sent at temperature 0 (311 positions) | 0.0190 | — |

- The 2.25-bit model sits about 10× further from hosted than the two engines sit from each other: the gap is the
  quantisation, not the engine.
- The native MXFP4 weights close 88 % of it. On the 311 positions where the hosted API agreed with itself up to its
  first divergence, native MXFP4 sits 0.0053 from hosted, the 2.25-bit build 0.042, and hosted from itself 0.019: the
  hosted API is not deterministic at temperature 0, and native MXFP4 is within that noise. [QA-11](cards/QA-11.md).

## Reproduce

- QBENCH: `tools/qbench/README.md`. Build `ds4_iq_helper_bench` and `ds4_helper_rt_bench` with `tools/dsv41/build.sh`,
  the references with `tools/qbench/build-ref.sh`, make the expert pools with `tools/qbench/mkpool.py`, then
  `tools/qbench/run-card.sh` on one card.
- Validation: `validation/README.md`. The prompts, the hosted answers and all token ids stay private; the tools print
  numbers only.
