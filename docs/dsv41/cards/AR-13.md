# AR-13: Making the host-memory decode all-reduce itself cheaper: three bit-identical variants, about 3 µs a call at most; parked
Status: parked (bench only; the whole bundle is about 0.09 ms a token, below what a served A/B can resolve) · Date: 2026-11-18
Code: not in the release commit of Gary, our fork of Strata (bench variants on two internal branches only). Flags: none (bench only).

## What and why
- Decode keeps the host-memory all-reduce ([AR-10](AR-10.md)). A desk study from a served kernel trace put it at about 0.83–0.94 ms of each decoded token at one user (7–8 %): 80 all-reduces a step (two a layer), all four-row windows of 80 KB a member, each about 29 µs after the last card arrives (INFERRED from the trace). No bit-identical design removes a call, since each one's output feeds the next, so the question was the cost per call.
- Variants, each the same sums in the same order (bit-identical by construction): **overlap** (read a peer's rows as soon as its flag is up, while the own put is still draining); **host reduce-scatter** (the engine's existing two-phase kernel plus the post step); **preloaded post** (load the post step's inputs during the wait, so the post after the sum runs from registers). A **post-off** variant that skips the post step entirely was run as a diagnostic only.

## Prediction
- Round 1: overlap 29 → 16–20 µs a call at T4 with the lead card last (ratio 0.45–0.75). Pre-registered: yes. OUT.
- Round 2: preloaded post saves 5–9 µs at T4; pass bar 3 µs plus the baseline's own noise (3.32 µs). Pre-registered: yes. OUT.

## Correctness
- Round 1: 109 of 109 checks PASS, 2.0 million calls compared word for word with the engine's kernel; soaks clean (MEASURED). Five baseline-variant arms did not run (a parser bug in the bench), so those checks are NO DATA, not passes (REPORTED).
- Round 2: 96 of 96 checks PASS, the sum and the post step's output both compared; 0 missing arms; soaks clean (MEASURED).

## Timing
- 18 Nov, the test machine's four XTX, bench only, T = rows a call (T1 = 20 KB a member, T4 = 80 KB). Round 2 kept each card busy before every timed call so that clocks were at their serving level (round 1 ran with idle, low-clocked cards).

- What the post-off diagnostic showed: the post step folded into the all-reduce's tail cost about 10 µs of a T4 call with idle clocks, but only about 4 µs with serving clocks. Round 1's "25–30 % faster" post-off figure is that cost, not a usable gain (REPORTED from the bench's in-kernel stamps).
- Overlap did not overlap: the lead's own put took about 5.8 µs, not the budgeted 9.5, and with reads in flight it slowed by about 4 µs, cancelling the saving for the other cards (REPORTED from the stamps; the shared bottleneck is INFERRED).

## Verdict
- **No variant is worth a port at decode sizes.** The real slack in a served-like T4 call is about 3–5 µs of about 30. Preloaded post plus overlap together would save about 0.25 ms a step, about 0.09 ms a token at one user (about 0.7 %) and about 0.5 % of a four-user step (INFERRED), below the 1–3 % rep-to-rep noise of a served A/B.
- Decision (18 Nov): park the per-call line; keep the variants in the bench. Revisit the host reduce-scatter and a block cap only if verify windows of eight rows or more become routine.
- The larger decode communication cost is not this exchange but the lead card's wait for the MI50 helpers and the CPU lane, about 10–12 ms a step (INFERRED from the same desk study).

## Reproduce
- No published bench.

## Notes / caveats
- Bench calls, not served steps. In serving, launch skew and the lead card's late arrival dominate the wait; a cheaper exchange shortens only the part after the last card arrives.
- Preloaded post and overlap were never built together, so whether they add is unknown.
