# HX-28: Expert picks summed twice: the expert cache and device-direct MI50 windows (a correctness bug, fixed in build 16)
Status: fixed in this release (`DS4_EC_FIX=1`, build 16) · Date: 2026-11-14
Code: the bug is in every build before 16 run with the expert cache on (the default) and `DS4_HELPER_DD=1`. The fix, `DS4_EC_FIX=1`, is in Gary's release commit (build 16; default off in the code, on in the recommended environment). The audit build that counted the double picks (`DS4_DD_AUDIT=1`, counts only) is not in this release.

## What and why
- HX-26's leak fix left one question open. When the expert cache moves an expert that an MI50 holds into XTX memory, the MI50s' device-direct tables, fixed at load, still list it. Is that expert then computed on both sides, and both results added?
- An audit build counted, at every device-direct window, the picks that were both in XTX memory and in an MI50's table, without changing the output. Served, 4 slots, HX-26's method: a fresh server, 8 greedy prompts, 50 cold 2K prompts, 3 × 8K, then the 8 greedy prompts again. Arm A: the cache as before; arm F: with `DS4_EC_FIX=1` (10 prompts, a control).

## Prediction
- About 2 % of device-direct picks summed twice in A (0.2–8 %); exactly 0 in F. Pre-registered: yes, before the run.

## Correctness
- The audit build with its counter on gave the same answers as the build without it, on a fresh process, 8 of 8 (MEASURED).
- Arm A's answers to the 8 greedy prompts after the 53 prompts differed from its fresh-process answers in **8 of 8** (MEASURED). With the fix, the answers were the same before and after, 8 of 8 (HX-26 addendum, MEASURED).

## Timing
- 14 Nov 09:14 UTC, 4 × RX 7900 XTX + 4 × MI50 at 135 W; the build-16 line with the fix switched off as build 15's behaviour (build 15 runs the same cache code [I]).

## Verdict
- **A real correctness bug: double count confirmed.** With the expert cache on and device-direct windows, each prompt read could move up to 8 MI50-held experts into XTX memory; from then on every pick of one of them was computed on the XTX and on its MI50, and both were added. By the end of 53 prompts that was about 5 % of all device-direct picks, half of them on a stale MI50 input. The output was not the model's true output, and it changed with the server's uptime. The answers stayed fluent and read correct (HX-26), which is why it went unnoticed.
- **Who was affected:** any process with MI50 helpers, the expert cache on and `DS4_HELPER_DD=1` (how builds were served up to build 15) once it had read a prompt; the count starts with the first prompt and grows with every one. A fresh process starts clean.
- **The fix:** `DS4_EC_FIX=1` stops the cache from moving MI50-held experts: 0 picks summed twice, no leak (HX-26), and the same answers before and after 53 prompts. It is in build 16's recommended environment. Keep it on whenever the expert cache and `DS4_HELPER_DD` are both on; `--no-expert-cache` also avoids the bug, at a higher cost (HX-26).
- **Its price:** the cache's gain on 8K prompts came from these moves. Served 8K first token 5.9 s on build 15, 6.7 s on build 16 (SV-16). Keeping the gain without the bug needs the MI50 tables to follow the cache's moves (not built).
