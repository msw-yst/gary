# HX-32: Swap instead of evict (`DS4_ECSWAP`): a long-running server keeps its prompt speed
Status: kept (build 18, staged; re-validation pending; not in the published release) · Date: 2026-11-15
Code: not in the published release; the code is not in the public commit. `DS4_ECSWAP=1`, default off, on top of `DS4_ECOWN=1` (HX-30).

## What and why
- With `DS4_ECOWN=1`, when the cache moves a hot expert from an MI50 up to an XTX, it pushes a cold expert off that XTX. No MI50 holds the cold one, so it falls back to the host-RAM path. Over a server's life those build up (the leak of HX-26, reopened).
- The moved expert's slot on its MI50 is no longer used. This change copies the cold expert into that slot and hands it to the MI50. Memory on each side stays the same.
- The handover is staged: copy first and read it back; then change the owner at a step boundary, so a step never sees half a state. No pick may be dropped or counted twice; an audit checks both.

## Prediction
- One user, 2K first token after 50 earlier prompts on one server: −8 % (−14 to −3). Fresh-server cells unchanged within ±1–2 %. 2K and 8K decode −0.03 ms (−0.10 to +0.03). Pre-registered: yes, before the run. Amended before the run: decode cells are read together with each request's draft acceptance (from HX-31's follow-up).

## Correctness
- **check 0, switch off:** identical to its base (build 17 + `DS4_SETTLE_AFTER=2`) and to build 16's reference runs (MEASURED).
- **check 1, switch on, cache off:** identical (MEASURED).
- **check 2, served, cache on:** 560 handovers, all 560 copies read back and matched; 631 table audits: **0 counted twice, 0 dropped, 0 table mismatches**. Double-count audit, 2.92 million picks, 0 twice; 580,008 cross-device checks, 0 mismatched (MEASURED).
- **check 3, a 200-prompt churn soak:** 1,592 handovers, all copies checked, 1,792 table audits: 0 twice, 0 dropped, 0 mismatches, 0 fallbacks. Experts on the host-RAM path stayed at 0 throughout, and each MI50's expert count stayed fixed (2,230 / 2,230 / 2,229 / 2,229) (MEASURED).

## Timing
- 15 Nov, same machine and client as SV-17. Served A/B, rounds base, swap, swap, base. The "life" cell reads a 2K prompt after 50 earlier prompts on the same server.

## Verdict
- **Kept: correct under heavy churn, and it does what it was for.** The host-RAM path stays empty, and a long-running server's first token is 22.7 % faster after 50 prompts. Fresh-server cells don't change, as predicted. 8 of 10 predictions came in.
- No measured per-step cost: the 2K decode cell is a token-path effect.
- Build 18 = build 17 + `DS4_ECSWAP=1`: staged, re-validation pending.
