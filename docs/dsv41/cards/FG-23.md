# FG-23: Making the CPU lane itself faster: five levers, none adopted; the lane kernel already runs near the memory ceiling
Status: dropped (all five) · Date: 2026-11-18
Code: not in the release commit of Gary, our fork of Strata (internal branch only). Flags (branch-only, default off): an LFU policy for the RAM store, `DS4_STORE_LANEFIRST=1` (lane-first expert order), `DS4_MX_PF` (prefetch distance in the lane kernel); thread pinning by `taskset` at launch; a low-bit lane format (desk only).

## What and why
- FG-22 put the CPU lane at up to a quarter of a native decode step. Before moving experts off it, five ways of making the lane itself faster were measured.

## Prediction
- Store policy: LFU cuts lane misses to ≤ 0.70× and one-user 2K decode to ≤ 0.98×. Lane-first order: decode × 0.88–0.96. Pinning: decode ≤ 0.97×. Prefetch and low-bit: bench gates.

## Correctness
- LFU store: bits PASS, 6 of 6 equal across arms (MEASURED).
- Lane-first order: **bits FAIL** (outputs differ at three positions): a bug in the reorder (MEASURED).
- Pinning, prefetch, low-bit: bit-identical by construction (the low-bit tiers bit-identical to each other in the bench) (MEASURED / INFERRED).

## Timing
- 18 Nov, the test machine (4 × RX 7900 XTX + 4 × MI50, one EPYC Zen 2 16-core host, DDR4-2666); native MXFP4 pack, internal native build. CPU benches with no GPU work; served A/Bs interleaved (ABBA).

## Verdict
- **None adopted.** The lane kernel is within 10–15 % of what the memory can deliver, so a faster kernel buys at most about 0.4–0.6 ms a step (INFERRED); its store already hits 95–97 %; pinning gains about 1 %; LFU is no better than LRU; the lane-first reorder changes outputs (a bug, to diagnose before any retry); a low-bit lane is compute-bound on these cores.
- **What is left is moving bytes off the CPU:** fewer experts on the lane (FG-22). Faster RAM raised the ceiling 14–16 % on 19 Nov (HW-13); its effect on lane decode has not been measured.
- A correction made the same night: the 1 GB/s of host disk reads first attributed to decode page-ins were prompt reads. Decode reads 0.28–0.34 GB/s (the store misses) with I/O pressure under 1.1 %; decode is not I/O-bound (MEASURED, re-cut per request).

## Reproduce
- No published run: the native build is not in a release. The bandwidth benchmark: any pinned read benchmark against the lane kernel's own timing.

## Notes / caveats
- Two earlier served runs that night carried a sampler pinned to the core where the engine's lane thread spins; their A/B ratios stand (same in every arm), their absolute times do not (ME-15).
- One LFU arm ran with only 6.4–6.7 GiB of memory free (an explicit store size sized wrongly); explicit store sizes were then barred until re-derived.

## Addendum (22 Nov)
- **Correction:** `DS4_MX_PF` is not branch-only; it is in build 17's release code. Its in-engine result (+0.146 / +0.712 ms a token at 512 / 1,024 bytes) is in FG-33.
