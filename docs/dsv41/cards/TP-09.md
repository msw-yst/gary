# TP-09: A layer split (pipeline) of the four XTX for more users: not viable for decode
Status: dropped (closed: the existing layer split ran on 14 Nov and lost for prompts and decode) · Date: 2026-11-13 (run 2026-11-14)
Code: existing layer split (`--tp 2` over two groups); no pipelined decode exists. Flags: none new.

## What and why
- Idea: instead of four-way tensor parallel (two all-reduces every layer), give each XTX a block of layers (pipeline, pp4) or run two two-way groups in a pipeline (tp2 × pp2), with several users' micro-batches in flight, to raise multi-user throughput. A third variant: two independent two-card engines.
- The claim behind it, that all-reduces are ~30 % of the time, is true for prompts (about 45 % of a 1K-row chunk) but not for decode.

## Prediction
- At 8 users: pp4 −17 % (155 vs 186 tok/s measured), tp2 × pp2 −7 % (174); at 4 users −24 % / −10 %; single-user latency far worse (pp4 about 35 ms a token). Pre-registered: yes, in the study note.
- Calibration rule for the one cheap test (the existing layer split, one user): close the idea if it takes more than 18.0 ms a token; only ≤ 16.0 ms would justify a build.

## Correctness
- Not run.

## Verdict
- **Not viable for decode throughput:** decode all-reduces are about 2 % of a step, and splitting users into micro-batches re-pays the ~10.6 ms fixed step cost each time. Two engines do not fit in VRAM or host RAM.
- The real multi-user limit is prompts read one at a time (SV-11), where all-reduces are a large share; concurrent prefill is the separate idea that may pay.

## Reproduce
- No published run: the code is in the release commit (the existing `--tp` layer split); a scripted public re-run has not been prepared.

## Notes / caveats
- The split of the fixed cost between dense reads and per-layer latency is estimated, not measured; the calibration run would pin it.

## Addendum (2026-11-14): the existing layer split measured, for prompts and decode
- Build 15, no new code: T4 = deployed tp4 with the prompt helper, S2 = `--tp 2` (two stages), S1 = `--tp 1` (four stages), T4OFF = tp4 helper off at 2K; prompts 2K, 8K, 32K, one cold process a prompt, then 32 decode tokens, drafter off. Pre-registered: S2 and S1 slower than T4 at every length (the desk said 2–4 ×). All 16 arms valid; S2 and S1 held 105 % and 118 % of T4's VRAM experts (MEASURED, layer-split.txt).
- **Prompt reads, ratio to T4: S2 2.62 × at 2K, 1.74 × at 8K, 1.52 × at 32K; S1 5.16 × / 3.59 × / 3.44 ×** (32K: T4 17.8 s, S2 27.0 s, S1 61.2 s). The engine refuses the prompt helper with more than one layer group, as the desk said (MEASURED, layer-split.txt).
- **Decode after the prompt: T4 14.85, S2 20.56, S1 24.36 ms a token** (predicted 14.4 / 20.0 / 27.0, all in) (MEASURED, layer-split.txt). S2 is above the 18.0 ms close line of the calibration rule above; the run used 32 tokens after each prompt, not the planned 256-token one-row line, but the margin is large [I].
- **Closed as built:** a layer split loses at every measured length for prompts, and its one-user decode is past the close line. The gap narrows with length (S2 2.6 × → 1.5 ×), so a split would only compete for prompts if the helper worked across groups; not pursued.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
