# HX-30: A cache fix that keeps promotion and counts each pick once (`DS4_ECOWN`)
Status: kept (in build 17, release 3) · Date: 2026-11-14
Code: in Gary's release commit (release 3). `DS4_ECOWN=1`, default off; it refuses to load together with `DS4_EC_FIX=1`. Three test-only switches come with it (a fixed-timing cache mode, a cache freeze and a batch-test warm-up), all off by default.

## What and why
- HX-29 showed that build 16's fix (`DS4_EC_FIX=1`) costs one user 4.6–8.4 % a token and 12 % on the 8K first token, because it stops the cache moving hot MI50-held experts into XTX memory.
- Where the double count comes from (read from the code): a cache move updates only the lead XTX's table. The MI50s' tables are set at load and never change, so a moved expert was computed on both sides and added twice.
- The fix: each request the lead sends an MI50 carries a mark on every pick the lead now holds in VRAM, read from the same table snapshot as its own plan. The MI50 skips marked picks, and the lead neither waits for them nor adds them. No table is rewritten while running, so there is no race with work armed a layer ahead.
- About 85 lines of new logic, plus the double-count audit, carried over unchanged.

## Prediction
- Against build 16, one user: 2K −0.30 ms a token (−0.50 to −0.10), 8K −0.45 ms (−0.90 to −0.10), 8K first token −10 % (−15 to −5); 4 and 8 users ±3 %. Pre-registered: yes, before the run.
- The design warned that part of HX-29's decode gain may come from the wrong sum, so the decode cells might not come back.

## Correctness
- **check 0, switch off:** identical to build 16 on short prompts with the drafter off and on, the batch test, 32K, 110K and one served user (1,025 token lines) (MEASURED).
- **check 1, switch on, cache off:** identical to build 16 on the same arms except 110K (MEASURED).
- **check 2, served, cache on:** 2.92 million picks, **0 counted twice**, 926 cache moves, 520 moved experts still in an MI50's table and skipped there; 578,604 cross-device checks, 0 mismatched (MEASURED).
- **check 3, batch against single requests, cache on, fixed-timing mode:** batches of 1, 2 and 8 all identical to their single runs; 0 counted twice (MEASURED). Without the fixed-timing mode, batch and single may differ legitimately, because the cache lands its moves on a time budget [I].

## Timing
- 14 Nov, same machine and client as HX-29. Served A/B, rounds build 16, new, new, build 16. Each round also ran an audited probe.

## Verdict
- **Kept: correct, and faster on prompts.** The prompt-time loss of build 16 is recovered in full; most of HX-29's decode gain is not. 4 of 5 predictions came in.
- The 32K cold read is 2.7 % slower. Disk is ruled out and the cache's settle step explains only part of it (HX-31). Cause not shown.
- Goes into build 17 with the batched-path fusion (SV-17).

## Reproduce
- `DS4_ECOWN=1` with `DS4_EC_FIX` unset (release 3). The served A/B client is not published.

## Notes / caveats
- With this switch, experts pushed off the XTXs build up on the host-RAM path over a server's life; HX-32 fixes that.
