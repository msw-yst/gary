# FG-28: The MXFP4 expert kernels: a bit-identical lookup fix (−22 to −27 % a call), then an 8-variant ladder: MI50 −13 to −31 %, XTX already at bandwidth
Status: kept (the lookup fix, in the native builds) / finding (the ladder: default off) · Date: 2026-11-17
Code: not in the fork's release commit. The lookup fix: internal build `mxfp4perm-r1` (commit c18a7159), ported into the native build (`nat18-r1`, d2a73071) and so into the later stack builds. The ladder: internal build `k4-r4` (90988acc), carried into the stack build (`stack-r2a-rc1`, 8c7aa75e) default off. Bench: `ds4_iq_helper_bench --pool-file` (HX-33). Flags: none for the fix (always on in those builds); `DS4_MXK=0..8` for the ladder (0 = the fixed kernel).

## What and why
- QBENCH found our MXFP4 expert path 1.5× slower than the references on the MI50 (HX-33) and 1.4–2.3× slower on an XTX (FG-19). A review of the gfx906 code found the cause of much of it: the E2M1 → int8 lookup used CUDA's `__byte_perm`, which HIP emulates in about 32 extra instructions a word. The fix uses `__builtin_amdgcn_perm` (one `v_perm_b32`) and plain global loads. Instruction count in the hot loop: gfx906 477 → 253, gfx1100 459 → 220 (REPORTED, from the disassembly); offline, the new lookup matched the old for all 2^32 inputs (REPORTED).
- A desk plan then set rooflines for one whole expert (18.80 MB at batch 1) and built an 8-variant ladder (persistent rows, prefetch, scalar offsets and a split dot, a repacked blob, a fused one-launch window, any row alignment for the lead's slices, activations staged once in LDS), every variant designed bit-identical to the fixed kernel.

## Prediction
- Lookup fix, pre-registered: one-token path, batch 1: MI50 kernel 45–52 µs, call 56–63 µs; XTX kernel 30–40 µs, call 39–50 µs.
- Ladder, pre-registered: busy time a call at batch 1, MI50 72 → 37–54 µs, XTX 47.6 → 29–40 µs.

## Correctness
- Lookup fix: old against new, BITWISE on all 18 A/B lines on each card (both paths, batch 1–8), and the control (old against itself) BITWISE (MEASURED).
- Ladder: every variant BITWISE against the fixed kernel on both cards (7–9 lines each), except variant 6 on the XTX (1 line; it hangs) (MEASURED).

## Timing
- 16 Nov (fix) and 17 Nov (ladder), one MI50 and one XTX in the 4 XTX + 4 MI50 test machine; real native MXFP4 expert bytes. GPU µs from a kernel trace (KT); busy p50 from back-to-back calls (QB); 4 rounds.

## Verdict
- **The lookup fix is kept:** bit-identical on both cards and 22–27 % faster a call at batch 1. It is in every native build since 16 Nov. Its served effect was small (0–5 %), because native decode was then bound by the CPU lane and the MI50 joins, not by expert kernels.
- **The ladder is a ceiling result.** On the XTX the real lead shapes already run at 89–104 % of peak, so the XTX expert kernels are done. On the MI50 the ladder found −13 % at batch 1 and −28 to −31 % at the verify batches, all bit-exact, but projected end to end at only 1–3 %; the bigger MI50 lever is the memory access pattern and the round trip, not the instructions. The variants stay in the code, default off; later MI50 kernel work built on variant 3's arithmetic.

## Reproduce
- Not reproducible from the release: the fix and the ladder are not in the public commits. The bench and its method are as HX-33.

## Notes / caveats
- One card of each kind, one run each.
- **Correction:** the XTX's pre-fix one-token call on this machine was 48.4 µs; FG-19's 70.8 µs was measured on an XTX in a second machine. So the XTX gain from the fix here is 48.4 → 35.5 µs.
- The XTX old-kernel rounds varied (one-token kernel 41.8 / 33.9 µs); the new kernel's rounds did not.
