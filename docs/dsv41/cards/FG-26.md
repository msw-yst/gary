# FG-26: What the 10.2 ms of decode attention is made of (desk ESTIMATES): mostly launch latency, about 525 launches a token on each XTX, and the ranked levers
Status: desk (estimates only; the timer build that would measure the parts is coded, not run) · Date: 2026-11-20
Code: no engine change. A timer build that splits the attention stage into 13 parts (`DS4_PROF_ATTN`, with `DS4_PROF_FROM` and a per-token log) is on an internal branch, compiled, not run.

**Every number on this card is a desk ESTIMATE (INFERRED: arithmetic on the code and on FG-25's measurements) unless it is marked MEASURED.** None of the estimates has been checked on a GPU.

## What and why
- FG-25 measured decode attention at 10.21 ms of a 22.2 ms token, the same at 2K and 8K (MEASURED). This desk study reads the code to say what that stage contains and where the time could go.

## What "attention" contains (from the code)
- Everything from the layer's start to the end of its attention all-reduce: the Engram step on its two layers (with its own all-gather), the HC mix / split / norm on the attention side, the input projections, the q / KV row finishing, the query projection and RoPE, the compressor on its four layers, the indexer with its top-k on its eight layers, the sparse attention itself, the output projections, and the all-reduce with its post step.
- **The wait for the slowest XTX is inside the all-reduce kernel, so it is inside "attention".**
- About **13–14 kernel launches a layer**, so **about 520–560 a token on each XTX** (about 525 used below).

## Where the 10.21 ms could go (ESTIMATE)
| part | ms a token | basis |
|---|---|---|
| reading the attention weights | 2.0–2.6 | about 1.8 GB a token on each XTX if the dense weights are 8-bit (Q8_0); about 4 ms if BF16. Which one is not settled. |
| gaps between launches | 1.7–1.9 | about 525 × 3.3 µs; a 3.2–3.3 µs untraced gap was measured on this box earlier (MEASURED there) |
| small fixed-latency kernels | 2.5–3.5 | about 300 non-GEMV launches at 5–8 µs: norms, RoPE, roundings, sparse attention on 16 heads, the indexer's score and top-k |
| the all-reduce | 0.6–1.0 | about 42 calls of 10–13 µs, plus the wait for the slowest member (unknown) |
| the profiler's own marks | 0.3–1.0 | the timed run was × 1.118 on the wall (MEASURED) |
| **sum** | **about 7.1–10.0** | brackets the 10.21 measured |

- Per layer: 10.21 ms ÷ 40 = 255 µs (MEASURED arithmetic), of which the weight bytes explain about 45–55 µs. That leaves about 200 µs over about 14 launches.
- The host is not the bound on average: it issues a token's layers in 9.07 ms and then waits 11.52 ms for the result (MEASURED). The per-launch cost is on the GPU side.
- **So attention is mostly latency, not bandwidth**, which fits it being the same at 2K and 8K: the KV and indexer reads are only about 10–20 MB a token.

## Levers, ranked by estimated saving a token, one user (ESTIMATE)
| # | lever | saving | risk |
|---|---|---|---|
| 1 | one persistent kernel for the whole attention block | 1–2 ms | very high (in-kernel all-reduce plus grid barriers can deadlock) |
| 2 | targeted fusions of the remaining chain (about 5–7 fewer launches a layer) | 0.8–1.5 ms | medium; each checkable bit for bit like the existing fusions |
| 2a | — the cheapest: the existing fused rounding for the output projection, extended to 8-bit weights | 0.15–0.25 ms | low |
| 3 | graph capture of the decode step | 0.8–1.0 ms of attention, 1.5–2 ms a whole step | high (per-token arguments must move to the device) |
| 4 | 4-bit attention weights | about 1.0 ms if they are 8-bit today | quality cost; needs an evaluation |
| 5 | the multi-workgroup top-k below 8K, or skipping it when the candidates are fewer than k | 0.1–0.3 ms at 2K | low |
| 6 | overlapping the attention all-reduce with the next projection | 0.05–0.2 ms | low-medium (a true dependency limits it) |

## Verdict (desk)
- Run the timer build first (about 27–30 GPU minutes, ESTIMATE): it turns this table's ranges into measured parts and settles the weight format and the member skew.
- Then the small exact fusions (2a, the output finish into sparse attention, lever 5) regardless of its result. The persistent kernel and graph capture are design decisions that make sense only if the measured parts show the small fixed-latency kernels as the largest bucket.

## Notes / caveats
- Not measured. The dense attention weight format of the native pack (8-bit or BF16) and the all-reduce wait for the slowest member are open until the timer build runs.

## Addendum (22 Nov)
- **Measured follow-up in FG-29 (22 Nov).** The attention weights are BF16 (settled); the all-reduce wait listed as unknown measures about 10 µs a call; the graph-capture lever's 1.5–2 ms a step is refuted, about 1 % served (FG-32).
