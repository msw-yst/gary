# PF-17: The short-prompt cutoff on the native pack: a fixed cost a prompt against a cost a token, and code moves the crossover
Status: finding (no cutoff adopted yet; 1,250 and 1,600 NO-GO, a ~1,000 confirm run proposed) · Date: 2026-11-17 (cutoff runs 2026-11-19)
Code: not in the release commit of Gary, our fork of Strata (internal branch only: the native build). Flags: `DS4_CHUNK_MIN` / `DS4_PICK_MIN` (the prompt length from which a read takes the chunked path; 512 in the native build's default) (branch-only).

## What and why
- A prompt read takes one of two paths. Under the cutoff it runs in small windows, like decode: experts that the XTXs do not hold are computed where they live, so the cost grows with the number of new tokens. At or over the cutoff it runs in chunks, and each chunk first sends every expert the XTXs do not hold to the XTXs (PF-15): about 15 s whatever the length on native, then a little per token.
- So there is a crossover length. Below it the window path is faster; above it the chunked path is. On the 2.25-bit pack the chunk cost is small, which is why 512 was a sensible cutoff there; on native it is not.

## Prediction
- Each run pre-registered bands per cell and a GO rule. The first run (cutoff 2,500 against 512): a band per cell, for example × 0.15–0.40 for a 600-token cold read. The second (1,250 and 1,600 against 512): GO if the median target ratio ≤ 0.65 and no target worse than 1.00.

## Correctness
- Every arm CONFIG ok, 0 bad steps, placement frozen (MEASURED). The cutoff changes which path a read takes, so text can differ from the baseline; what matters for A/Bs is that each arm repeats itself, which is ME-13's subject (13 of 13 identical in every arm of the second run, MEASURED).

## Timing
- 17 and 19 Nov, the test machine: 4 × RX 7900 XTX (tensor-parallel 4) and 4 × MI50 32 GB helpers at 135 W; native MXFP4 pack, internal native build, one user unless stated. Filler and code prompts, cold or as a new turn on a cached prefix of 6.5–11K tokens; two arms of each kind, interleaved.

- Content: code costs 1.69–1.80× filler a token on the window path, both cold (MEASURED). A cached prefix does not change the per-token cost (× 0.90–1.05 across three pairs): no prefix effect, so one cutoff serves (MEASURED).
- Gains at 1,250: filler 600 / 998 tokens × 0.26 / × 0.32; a 687-token turn × 0.60; a 1,079-token turn × 0.91; code cold 902 tokens × 0.84 (MEASURED).
- Losses: code cold 1,182 tokens × 1.06 at both cutoffs; at 1,600, code cold 1,519 tokens × 1.42 and a 1,510-token turn × 1.18 (MEASURED).
- Decode in the same cells was faster with the higher cutoffs (× 0.93 in the first run, × 0.86 in the second) (MEASURED; the cause was not measured).

## Verdict
- **The window path wins big on short reads** (2.4–3.9× at 600–1,000 cold tokens) **and halves other users' stall**, but it pays per token, and code pays 1.7–1.8× what filler does. With code the crossover is about 1,190 tokens; 1,250 and 1,600 both lose on code and are NO-GO by their rule. 2,500 was too high.
- Both cutoff runs are formally NO DATA: the first because one target cell took the window path in both arms (only 250 new tokens), the second because one control drifted (× 0.817). The per-cell numbers above are each arm's own.
- Next: a cutoff of about 1,000 as a confirm run, or a cutoff that looks at the content. Since then the chunked path itself became 4.6× faster at 2K (PF-20), which moves every crossover down; the cutoff has to be re-measured on that build.

## Notes / caveats
- Why code costs more a token on the window path is not measured. INFERRED: code routes to more varied experts, so each window touches more experts that live on the MI50s or the CPU lane.
- Prompt sizes are the engine's counts of new tokens; cell names in the run used target sizes.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
