# PF-10: The prompt's fixed cost: ~3.3 s a prompt, 58 % of prompt time under agent traffic
Status: finding (fix measured in PF-11; its validation is pending) · Date: 2026-11-11
Code: the measurement is on build 11 as deployed (in the fork's release commit). The proposed fix, `DS4_PF_HELPER=<rows>`, was built afterwards and is in the fork's release commit (default off; [PF-11](PF-11.md)).

## What and why
- Under agent traffic, reading prompts was about a quarter of the wall time even with ~95 % of each prompt reused from the cache (SV-08). The aggregate "tok/s" for prompts hides why, so this card fits the engine's own per-request lines.
- Each served request logs "prompt P tokens = R reused + N read in T ms". The 47 requests of the SV-08 session are the data.

## Prediction
- None for the finding: it is an observation. Pre-registered: no.
- The fix's prediction (below) was written before its test.

## Correctness
- Not applicable to the finding. The fix is not bit-identical (below) and needs the quality gate.

## Timing
- Hardware: 4 × RX 7900 XTX (XTX #1–3 Gen4 x16, XTX #4 Gen4 x8) + 4 × MI50 32 GB at 135 W (Gen4 x4 each). XTX at minimum power cap with −50 mV. MI50 DPM `high` (CP-03).
- Software: ROCm 7.14 on Linux; Strata v0.2.9 plus this fork's changes (build 11), 131,072-token context, drafter on.
- The mechanism comes from one profiled 2,048-token prompt on the same layout and build settings.

## Verdict
- **A prompt's time is a floor plus a slope, and the floor dominates agent traffic.** Every prompt chunk of ≥ ~700 tokens touches nearly every expert of every layer (6 picks a token over 384 experts), so each XTX streams its quarter of the host-RAM experts, 21.2 GB, whatever the chunk's length. At 6.17 GB/s that is 3.4 s, the floor. The slope is the same stream again for long prompts (0.427 ms × 8,192 = 3.5 s a full chunk).
- **The MI50s hold every one of those streamed experts in their own VRAM and are idle during prefill.** The CPU lane does nothing in prefill either.
- **XTX #4 is the slow member here too** (PF-09): its small stages take 2.0–2.4× the other cards' time, and the others spend the difference waiting in the all-reduces. That is more than its 2–3 % lower clock explains (HW-08); the cause is open.
- **Why the stream runs at ~6 GB/s on links good for ~25 GB/s is open.** Candidates: the platform's DMA, a small-row gather used for part of each expert, and contention with the peer-to-peer prompt all-reduce. A bandwidth test is built and not run.
- **Proposed fix, built:** `DS4_PF_HELPER=<rows>`: for prompt chunks up to `<rows>` tokens, the MI50s compute the experts they already hold, instead of the XTX streaming them. Each MI50 pulls only its tokens' rows and writes back weighted sums; the XTX stream nothing in those layers.
  - Prediction: the floor 3.26 s → 0.20–0.50 s, the slope 0.43 → 0.43–0.60 ms a token; a 2,048-token suffix ~3.5–4.1 s → 1.1–1.7 s; prompt time under the agent workload −35 to −55 %, wall time −8 to −15 %. A cold 240K prompt about unchanged.
  - Not bit-identical: the down projection's sum over four XTX slices becomes one sum on an MI50, and the experts run in different kernels. It needs the paired quality gate, which is part of its test.
  - **Measured since: [PF-11](PF-11.md).** A 1K suffix went 3.42 → 1.33 s and a 2K one 3.71 → 2.11 s; it is not bit-identical and its quality validation is pending.
- A second, exact option is designed and conditional on the bandwidth test: lay each member's expert parts out contiguously in host RAM so the whole stream is DMA.

## Reproduce
- Any Strata server's log carries the per-request prompt lines. Fit T against N for requests with N ≥ 700.

## Notes / caveats
- One session of one agent workload; the 700-token boundary and the fit depend on the prompt mix.
- The profiled prompt is a single 2,048-token run.
