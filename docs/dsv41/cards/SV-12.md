# SV-12: Two prompt-read hangs, and a build that names its own stall (`DS4_HANG_DIAG`)
Status: open (cause not found; the self-reporting build is in use) · Date: 2026-11-13
Code: not in Gary's release commit (internal branch only). Flags: `DS4_HANG_DIAG=1` (host-only diagnostics; unset = the old behaviour).

## What and why
- **Hang 1** (13 Nov 01:27, SV-11 arm B, prompt helper off, 4 slots): after six normal requests the server sat in "reading the prompt: 1,658 tokens" for 3,441 s until the phase timeout killed it. No GPU driver errors.
- **Hang 2** (13 Nov ~08:25, during CP-05, build 13, prompt helper on): a 15,464-token prompt stopped at exactly half (7,732 of 15,464) and printed the same progress line 20,837 times. All four XTX were 100 % busy, the four MI50s idle, five host threads spinning in user space. The two prompts before it (9,197 and 13,565 tokens) had completed normally in the same engine. The engine was stopped after 18 minutes (REPORTED from the diagnosis file written at the time).
- Because hang 1 had the helper off, the prompt helper is not the only path.

## Prediction
- From a read of the source (not a run): most likely (~55–60 %) a peer-to-peer prompt all-reduce of the second chunk spins forever, because its wait sets an error word after 2^24 polls but the production call passes "not fatal", so it never stops. That fits both hangs. A second candidate (members spinning on the lead's helper key, which has no timeout) predicts idle XTX and cannot happen with the helper off [I].
- "Exactly half" is the chunk split: the prompt was cut into two equal chunks of 7,732 rows, and progress advances per whole chunk, so the second chunk never finished. The earlier prompts had the same structure and completed, so it is a race, not a size rule [I].

## Correctness
- The diagnostic build changes host code only: the fat binary and every GPU code object are byte-identical to build 14, and the 14 all-reduce kernels' machine code is identical (REPORTED from the build notes).

## Timing
- The smoke run: 13 Nov 10:28, pre-incident hardware, 4 arms × 4 prompts (two long, two short): production; peer all-reduce off (`DS4_AR_P2PK=0`); prompt helper off; prompt skip off.

## Verdict
- **Not reproduced on demand, so not fixed.** The diagnostic build turns a silent spin into a named stop: the stalled all-reduce exits naming the peer and tile, every worker leaves a breadcrumb (chunk, layer, stage, all-reduce sequence) after 30 s without progress, and the helper-key wait gets a deadline. The smoke run showed it loads, engages and does not false-trigger on legitimate long prompts.
- The decision was to run the following long-prompt runs on this build with the diagnostics on, so the next natural hang names its site, and to take a stack dump before any kill. A deliberate hang-rate experiment (4 arms, a few hundred long prompts) is held in reserve if self-reporting does not name the site or hangs become frequent.
