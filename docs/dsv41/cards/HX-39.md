# HX-39: Batched MI50 helper windows (two or more tokens a window): the cause is the grid size; three kernel builds cut empty windows by 33–39 µs but lose it back on real work
Status: dropped (timing gate failed on all three builds; never run in the engine) · Date: 2026-11-14
Code: not in the fork's release commit (internal builds `helperbatch` 4472b39c, `helperbatch-lb` 8d1a0993, `helperbatch-hy` e856db88, each on build 16). Flags: `DS4_G906_HB=1` (first two builds), `DS4_G906_HY=1` with a grid-height option GY (third build); all default off.

## What and why
- When the MI50 helper serves two or more tokens in one window (several users, or drafted tokens), it leaves the gfx906 kernel and runs the portable one. A desk study read the code to find out why such windows cost so much.
- **Root cause: the grid size, not missing batching.** At T ≥ 2 tokens a window the portable kernel launches T × 8 groups' worth of blocks (19.5 k blocks at T 4, 43.8 k at T 9) for about 1–5 live experts. An empty window costs 23 → 59 → 116 µs at T 1 / 4 / 9, about 2 ns an empty block (INFERRED from the source and earlier bench numbers).
- Real work is about 37 µs per distinct expert and cannot be batched away: helper experts are cold, and tokens rarely share one (INFERRED).
- So the fix is to stop paying for empty blocks. Three builds tried:
  - **HB:** a fixed 120-block persistent grid that loops over live tiles only; T = 1 untouched; same per-row arithmetic.
  - **HB-LB:** HB with `__launch_bounds__(256, 2)` (2 waves a SIMD instead of 1). Bounds alone spilled registers, so its one-entry body also reloads its activations each item (same operations, same order).
  - **HY (hybrid):** today's portable kernels, unchanged arithmetic, on a (tiles, GY) grid that loops over live groups only.

## Prediction
- Desk: about −0.9 ms a step at 4 users (−3.4 %), −2.6 ms at 9, −0.5 ms at one user with drafter windows (INFERRED).
- HB and HB-LB bench gate: BITWISE in every cell; T 4 one-entry, one-group (G1) cell with the switch on no more than 5 µs above the T 1 G1 cell; no T 2–4 multi-entry cell worse by more than 2 µs; ABORT on any difference or a T 4 G1 gain under 10 µs. Pre-registered: yes.
- HY bench gate: a clean switch-off vs switch-off phase first (else VOID); then switch on BITWISE; PASS = T 4 one-entry G1 gain ≥ 20 µs for every expert type, no T 2–4 cell with G ≥ 1 worse by more than 2 µs, T 1 within ±1 µs. Expected −38 / −35 / −30 µs at T 4 G0 / G1 / G2. Pre-registered: yes.

## Correctness
- **HB and HB-LB: ABORT on identity (RC 4).** 3 (HB) and 10 (HB-LB) of 332 cells showed the gate_up output differing while the down output was BITWISE in every one (MEASURED). Pass 2 never ran.
- **The ABORT was the bench, not the kernels.** A desk check found that both paths write exactly the live rows. The bench had shown the same "gate_up differs, down bitwise" pattern on 12 Nov with the same kernel in both arms. The likely cause was the bench clearing its output on the default stream while the kernels ran on a non-blocking stream (INFERRED at the time).
- With the bench fixed to clear on its own stream, HY's switch-off vs switch-off phase was **BITWISE in all 1,004 cells**. That confirmed the bench fault (MEASURED). HY switch on: **BITWISE in all 1,004 cells × 2 passes** at GY 2, and in 1 pass each at GY 1 and 4 (MEASURED).
- The HB / HB-LB ABORTs were very likely the same bench fault (INFERRED). Their timing failures stand.
- Not run: an engine identity run. The HY build also recompiled 152 untouched gfx906 kernels differently (register and instruction order only; no floating-point or memory operation differs), so a bench pass would not have cleared engine use on its own (REPORTED from the build notes).

## Verdict
- **The cause is confirmed exactly, but no build passes its timing gate.** Removing empty launches saves 33–39 µs a window, as the desk study said. A small grid then serialises the live work and loses it back, worst where tokens share an expert. Two waves a SIMD halve the loss but do not remove it. The hybrid is exact everywhere and still loses from 2 live groups up.
- None of the three went into the engine. A possible next shape (a full grid where groups are likely live, a small one only where an empty window is likely) was left as a desk note.
- The same empty-grid waste in the MXFP4 window was later removed by a flat kernel that walks only live groups (HX-36).

## Reproduce
- Not reproducible from the published code: the three builds are not in the public commits.

## Notes / caveats
- **The HB / HB-LB bench summaries printed "met" for the T 1, multi-entry and gain rules while the cells show them failing.** With pass 2 missing, the script judged those rules over an empty set. Read the cells, not those three lines (MEASURED from the run; the reading is ours [I]).
- HB's gate_up kernel used 138–140 registers (one wave a SIMD); its down kernel was 129 (also one wave), so the first HB bench ran both kernels at one wave (REPORTED from the build notes).
