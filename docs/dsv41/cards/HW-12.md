# HW-12: MI50 peer reads return stale data after the MI50's own SDMA engine wrote it, until its HDP is flushed
Status: finding · Date: 2026-11-17
Code: no engine change. The engine only ever pushes data into another card's memory, never pulls from an MI50. The probe used here is not in this release.

## What and why
- Moving MI50 results straight onto the XTX cards needs peer-to-peer (P2P) traffic to be exact. A P2P map of the test machine (16 Nov) found every **write** exact and every **read of MI50 memory** wrong (MEASURED):
  - XTX ↔ XTX 12 of 12 pairs and XTX → MI50 16 of 16 pairs byte-exact, by copy and by kernel stores;
  - every pair that reads from an MI50 (16 MI50 → XTX, 12 MI50 → MI50) returned the **previous repetition's data** at 64 KiB, by copy and by kernel loads, with an uncached source too;
  - the same copies with `HSA_ENABLE_SDMA=0` (blit kernels instead of the copy engine) were exact on every pair.
- This card finds the cause. In short: data that the MI50's **SDMA copy engine** wrote into its own VRAM is read stale by peers until the MI50's **HDP** (its host data path, the PCIe-side cache) is flushed.

## Prediction
- Pre-registered readout: if an HDP flush on the owning MI50 between the write and the peer read removes the stale reads, the cause is the HDP; if only a settle delay does, it is a visibility race; if only a kernel-written source does, it is the SDMA write path.

## Correctness
- The probe re-seeds the source with a unique pattern every repetition, poisons the destination with the complement of the expected value, checks guard words around it, and waits for both cards before reading (REPORTED, from the probe's source). Pushes of the same freshly written source are exact at every size, so the MI50 holds the new data; the wrong words come from the path by which a peer reads MI50 memory (MEASURED).

## Timing
- 17 Nov, the test machine (Linux kernel 7.0): two pairs, MI50 → MI50 and MI50 → XTX, 200 repetitions a size, 8–128 KiB. Earlier the same day, a second machine with a different mainboard and Linux kernel 6.17.2: one XTX + one MI50, both at PCIe Gen4 x16. ROCm 7.14 user space on both. Not a timing run.

## Verdict
- **Cause found: the MI50's HDP after SDMA writes.** Data the MI50's SDMA engine wrote into its VRAM is read stale (CORRUPT) by peers until the owning MI50's HDP is flushed. Kernel-written data, blit-copied data and an explicit HDP flush all read exact; waiting does not help. By the pre-registered readout this is the HDP; a kernel-written source also reading exact fits it.
- **Why "stale from 32 KiB up":** the size threshold belongs to the *write*, not the read. ROCm's runtime copies host → device buffers of up to 16 KiB with a blit kernel and larger ones with the SDMA engine (`GPU_FORCE_BLIT_COPY_SIZE`, default 16 KB) (REPORTED, from the ROCm runtime source). Every stale cell on both machines had an SDMA-written source; every exact read cell had a blit-written one.
- **Not the Linux kernel, the board or the BAR setup:** it reproduces on kernels 6.17.2 and 7.0 on two different boards (MEASURED). The MI50 BARs sit below the card's 44-bit address limit and the kernels have P2P DMA (`PCI_P2PDMA`, `HSA_AMD_P2P`, `DMABUF_MOVE_NOTIFY`) enabled (REPORTED), so BAR-size and kernel-config fixes do not apply here (INFERRED). A driver swap is not a likely fix (INFERRED).
- **What to do on gfx906, in order of cost:**
  1. push, do not pull: write into the reader's memory (exact on every pair here);
  2. produce data that peers will read with a kernel, not an SDMA copy;
  3. force blit copies (`GPU_FORCE_BLIT_COPY_SIZE` above your largest copy), at some copy-bandwidth cost (not measured here);
  4. flush the owner's HDP after its SDMA writes and before any peer read (ROCr exposes the flush register's address as `HSA_AMD_AGENT_INFO_HDP_FLUSH`).
- This engine stays push-only, which is safe. MI50 pull reads become usable if they are ever wanted.

## Reproduce
- The full P2P write-up (platform checks, this repro, transport numbers, open questions): [p2p-on-gfx906-and-gfx1100.md](../p2p-on-gfx906-and-gfx1100.md).
- Any P2P test that (1) writes the MI50 source with a host → device copy over 16 KiB, (2) re-seeds it every repetition, and (3) reads it from a peer. Compare against `HSA_ENABLE_SDMA=0`, a kernel-written source, and an HDP flush between write and read. A single read of a freshly allocated buffer cannot show this failure: the stale data is the previous contents.

## Notes / caveats
- Two machines, one VBIOS family on the MI50s, ROCm 7.14. Other ROCm releases may choose copy engines differently.
- Why ROCr's own HDP flush before each SDMA copy does not cover this was not established; the measured fact is that an explicit flush after the write and before the read does.
- The cost of options 3 and 4 was not measured.

Numbers are labelled MEASURED (read from a raw run file or a script-written summary), REPORTED (from a commit message or write-up at the time, not re-checked against raw output) or INFERRED (our own reading).
