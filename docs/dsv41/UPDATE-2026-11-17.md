## The BF16 matvec: 4 served users +9.8 % on the native pack ([FG-20](cards/FG-20.md))

On the native MXFP4 pack the BF16 matvec was the lead XTX's largest kernel line (35 % of its traced kernel time). It
was latency-bound: one weight load in flight a lane. The new kernel keeps every lane's arithmetic in the same order
and only issues more loads at once.

| | switch off | `DS4_BF16MV=r2u4n` |
|---|---|---|
| kernel time at 4 rows (bench) | 1 | 0.51× |
| served verify step | 43.4 ms | 41.5 ms (−4.4 %) |
| 4 users | 109.1 tok/s | 119.8 tok/s (+9.8 %) |

Bit for bit on all 16 bench lines. The served step gain is smaller than predicted (× 0.956 against × 0.80–0.93).

## MI50 peer reads go stale after SDMA writes: the HDP ([HW-12](cards/HW-12.md))

For anyone using P2P on gfx906: data written into MI50 VRAM by the MI50's own SDMA copy engine (ROCm uses it for host →
device copies over 16 KiB) reads stale for peer GPUs until the MI50's HDP is flushed. Kernel-written data, forced blit
copies or an explicit HDP flush read exact; waiting 1 or 20 ms does not help. It reproduces on Linux kernels 6.17.2 and
7.0 on two boards. Writes into MI50 memory were exact on every pair we tried; this engine only pushes.

## Mixed precision: x25c closes about 60 % of the quality gap ([QA-12](cards/QA-12.md))

Native MXFP4 copies of the 2,960 most-used experts (about 19 %) on top of the 2.25-bit pack, all on GPUs: KL from
hosted 0.0438 → 0.0210 (native 0.0054), 1 user 8.117 → 9.586 ms a token, first token 2.24 → 2.54 s (native 18.4 s),
4 users 163.4 → 148.8 tok/s. The share of native experts sets the KL; which experts are chosen at a given share
barely moves it (INFERRED from two packs, mean KL only). Code not in this release.

## Drafting at four users is slower in a greedy test ([DR-10](cards/DR-10.md))

`DS4_BATCH_DSPARK_MAX=4` against 3 at four users, greedy, equal-length prompts: × 0.806 on build 17, × 0.932 on a
native build, × 0.787 on x25c. A drafted four-user step costs 2.0–2.8× a plain one but lands only 1.80 tokens a round
on build 17. The served setting stays 3. Served traffic samples and arrives unevenly; an earlier served test measured
4 over 3 at × 1.11 at short context (REPORTED), so one served A/B is still open.

## castagna-veloce against llama.cpp on four MI50s ([EB-09](cards/EB-09.md))

Same GGUF, four MI50s alone. The model does not fit in 4 × 32 GB, so decode is CPU-bound and about equal (4.6 against
4.4 tok/s); castagna-veloce's prefill is 1.40× (512 tokens) and 1.85× (2,048 tokens) mainline's, with its
virtual-device split off. Its published figure needs eight MI50s with the whole model in VRAM, which we did not test.
